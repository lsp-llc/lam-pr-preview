Memory and context

The Context Behind an 18 GiB Download

Qwen3-32B and Granite 4.0 h-small have similar Q4_K_M file sizes and very different growing attention caches. A sourced calculation explains the session budget.

By Sundog

7 September 2026

Two downloads can take almost the same space on disk and leave radically different room for a conversation. I want the session budget before committing to the download. That starts with the attention layout in the model configuration.

The official Qwen3-32B Q4_K_M file is 18.40 GiB. IBM's Granite 4.0 h-small Q4_K_M is 18.14 GiB. Close enough to occupy the same shopping shortlist. Their growing FP16 attention caches cost 256 KiB and 16 KiB per token respectively, under the configurations below. At a long context, that small architectural detail overtakes the difference between the downloads.

[OPINION] I would read the attention layout before spending an afternoon downloading a model for long sessions. I want the conversation I came for, including its awkward length and the answer at the end. Weight size helps choose the candidate; the cache layout tells me which session to try.

A comparison you can reproduce before loading

Use one sequence, FP16 keys and values, and a runtime that stores the attention cache in the layout described by the model. For ordinary grouped-query attention, the growing payload is two times the attention-layer count, times KV heads, times head dimension, times bytes per value, times cached tokens. The factor of two counts keys and values.

KV bytes = 2 × attention layers × KV heads × head dimension × bytes per value × tokens

Qwen3-32B has 64 layers, 8 KV heads and a head dimension of 128. At two bytes per value, that gives 262,144 bytes per token. Granite has four attention layers with those same head dimensions and KV-head count, plus 36 Mamba layers. Its growing attention term is 16,384 bytes per token. The Mamba layers need recurrent state; omitting them from the growing KV term does not make their memory free. Qwen configuration; Granite configuration.

The final column is a planning subtotal. It excludes recurrent state, runtime workspaces, padding, temporary prefill allocations and other processes. Disk storage can also differ from loaded tensor storage. I did not test either model's maximum context on a 24 GiB device. The 20.14 GiB subtotal makes Granite a candidate to investigate at its declared 131,072-token window; it establishes no successful load or generation.

The sixteenfold ratio applies to the growing attention cache. It says nothing about a sixteenfold reduction in total memory, or which model will answer better. Those are different comparisons.

The layer count can send you in the wrong direction

Sliding-window attention adds another trap. A full-attention layer keeps growing with the sequence; a correctly bounded sliding layer can stop growing after its window fills. Averaging both into one constant bytes-per-token number hides the context length used to calculate it.

OLMo 3.1 32B has 16 full-attention layers and 48 sliding layers with a 4,096-token window. At 65,536 tokens, a simplified cache that honors those windows has the storage of 19 full-length layers: 16 + 48 × 4,096 / 65,536. Treating all 64 layers as full attention overstates that term by about 3.37 times. Four times describes the long-context growth ratio, not the total at this window. Pinned OLMo configuration.

The runtime must honor the layout for that arithmetic to help. llama.cpp exposes --swa-full, which changes how sliding-window cache is allocated. Its default fitting behavior adjusts unset settings; your explicit context request and the runner's actual allocations still matter. These details were checked at revision 465e49b9cea7. Read the startup log from your build. Argument implementation; defaults.

Quantizing the cache changes the next experiment

Weight quantization and cache quantization are separate choices. In llama.cpp's block layout, 32 FP16 values occupy 64 bytes. A q8_0 block occupies 34 bytes; q4_0 occupies 18. That makes the payloads 53.125% and 28.125% of FP16, before allocation padding and other buffers. Pinned block definitions.

Apply that q4_0 ratio to the Qwen3-32B example and its 32,768-token attention payload falls from 8.00 to 2.25 GiB. The file-plus-KV subtotal becomes 20.65 GiB. That reduction justifies testing the cache setting. The whole session still needs a measured allocation.

Speed needs its own measurement. Memoriant's corrected April 2026 GB10 results used Nemotron-3-Nano-30B-A3B-UD-Q4_K_XL.gguf and llama.cpp build 8399. At 24K context, reported generation was 44.6 tokens/s with FP16 cache and 39.3 with q4_0; at 110K it was 38.0 and 24.0. The same report found essentially equal short-context speed. Those are results for that model and build, rather than a universal tax on cache quantization. Corrected benchmark and setup.

I have not reproduced that benchmark. On your runner, check the answers as well as generation speed. Saving cache memory is useful only if the output remains usable and the longer session is worth the latency.

Keep the effective context with the result

A runner can load a smaller context than the one you had in mind. Current Ollama source selects automatic defaults using VRAM-capacity tiers and permits one lower-context retry after an out-of-memory failure with automatically selected context. An explicit setting and the model's limit change that path. The checked revision is 83ed7d9965b1. Context selection; load retry.

Write down the effective context, cache dtype and parallel sequence count with the exact weight file and runner build. Send a prompt near your intended working length, leave room for the answer, and inspect the endpoint's finish reason. For llama.cpp, native truncation fields and an OpenAI-compatible finish_reason are different response surfaces. Response serialization.

Then check whether the answer still uses the part of the conversation you needed it to remember. Keep that result with the allocation record. The extra room has earned its keep when it carries the work through.

How to Choose a Local Coding Model for Your Actual Work

Test a local coding model on a small bug fix, compare successful changes and time spent, and use research to interpret the result.

By Sundog

Writing revised 13 September 2026

A practical comparison for people who can read a small amount of Python

You want a local AI model that can help fix bugs, change a script, or add a feature. A high coding score is useful information, but you still need to know whether the model can make the changes you need on your computer. Give two models the same small job, with a result you can check. Then compare the working code, the time it took, and how often you had to step in.

We will use a filename filter with a simple bug: it accepts report.csv but rejects REPORT.CSV. The example shows how to define success, catch an incomplete fix, and build a comparison that tells you more than how quickly a model produces text. You can try it in a chat window by copying the code yourself; an application that edits files automatically is optional.

Give the model a task with an answer you can check

Suppose a Python script imports files whose names end in .csv. Its filter currently looks like this:

def is_csv(name):
    return name.endswith(".csv")

The function expects a string and returns True or False. It is checking the filename only; it does not inspect the file's contents. Paste the function into your chat window with this request:

Change this function so it accepts a .csv extension regardless of capitalization. Keep rejecting other extensions. Preserve the function name and return type. Explain the change briefly.

Before reading the answer, decide what the result must do:

Checks for our illustrative bug fix
InputRequired resultWhy it matters
report.csvTrueThe behavior that already worked must survive.
REPORT.CSVTrueThis is the reported bug.
photo.pngFalseThe filter must still reject other extensions.
report.csv.exeFalseContaining “.csv” is different from ending in “.csv”.

A suitable fix for these requirements is:

def is_csv(name):
    return name.lower().endswith(".csv")

Converting the name to lowercase makes the suffix comparison insensitive to capitalization. By contrast, return ".csv" in name.lower() looks plausible but accepts report.csv.exe. A fluent explanation of that second answer would not repair its behavior.

You can run the checks with Python. Put the proposed function above these statements in a file:

assert is_csv("report.csv") is True
assert is_csv("REPORT.CSV") is True
assert is_csv("photo.png") is False
assert is_csv("report.csv.exe") is False
print("All four checks passed")

Save the function and checks together as filename_check.py. In a terminal opened in that folder, run python filename_check.py (or py filename_check.py with the Windows Python launcher). A failed assertion stops the script at the unmet check. The success message appears only after all four assertions pass. This assumes Python is already installed.

These are illustrative examples, not results from a coding-model comparison. We executed the original function, the corrected function, and the overly broad alternative: the original and the overly broad version each pass three of these four checks; the corrected version passes all four. That establishes this example's behavior, not the general quality of any AI model.

For a real project, also inspect the code changes and run the project's existing tests. Four checks can establish four requirements; they cannot cover everything an application might do. Add another capitalization pattern, such as Quarterly.CsV, and an unrelated filename such as csv_notes.txt to check that the change handles the rule rather than only the examples.

What coding research adds to a small test

Agentless, by Xia and colleagues, organizes software repair into three stages: locate the relevant code, propose a repair, and validate candidate patches. Its experiments use GPT-4o and SWE-bench software issues. The transferable idea is to inspect these stages separately. If the relevant function never reaches the model, changing the model is only one possible remedy. If a proposed fix fails the checks, a convincing explanation does not make it a successful repair. The paper does not establish how a particular local model will perform. [1]

The paper also examines a weakness in generated tests: reproducing a bug is not enough. A useful test must recognize when a correct repair resolves it. The authors check generated tests against the benchmark's reference repairs and find that many fail this second requirement. That is why our example includes expected results written before accepting the proposed fix. Tests are evidence whose quality matters, not an automatic guarantee of correctness. [1]

SWE-Effi, by Fan and colleagues, asks what changes when coding systems are evaluated under resource limits. It studies five software workflows paired with three API-hosted models on 50 SWE-bench Verified issues. The study considers task resolution alongside tokens, computation, and inference time. A workflow that finishes more tasks may also spend substantial resources generating candidates, running tests, or pursuing failures. Its findings motivate recording the whole attempt, including unsuccessful work. [2]

The experimental boundary matters. SWE-Effi's models were accessed through APIs; its normalized inference-time calculation is fitted to API logs. Those numbers are not predictions for your GPU. Our proposed local comparison below uses your observed task time and checks. It borrows the question about useful work per resource, without treating the paper's rankings as local hardware results. [2]

Compare the same work under conditions you record

One easy fix is a useful first check. It is a poor basis for declaring a model the best at programming. Build a small set from the work you actually do: a bug fix, a change to a data transformation, a feature with several requirements, or a repair that needs information from two files. Define the expected behavior before running the comparison.

Give each candidate a fresh copy of the same starting code, the same request, and the same checks. Set the same time limit and assistance policy. If you explain an error to one model, either give the other model the same opportunity or record the difference. Keep failed attempts in the record.

If you use a coding application that reads files and runs commands, keep that application and its tools consistent where possible. The language model proposes the code or action; the application carries out supported actions and returns their results. The software running the local model must also support the requested tool-call format. A model's ability to chat does not establish that this complete setup works. The llama.cpp function-calling documentation describes the relevant model and template support. [3]

Sometimes two candidates need different applications or formats. You can still compare the complete setups, but say what changed. Otherwise, an application difference can be mistaken for a model difference.

Measure success and the effort needed to get there

For each task, record whether all required checks passed, whether the existing tests still passed, how much time elapsed, and how much assistance you supplied. Decide in advance whether success must come from the first answer or may include revisions within a fixed allowance. Those are different comparisons.

A simple descriptive measure is:

Task success rate = successful tasks / attempted tasks

If eight of ten tasks succeed, the result is 80% for those ten tasks under those conditions. It is not an estimate that every future task has exactly an 80% chance of success. The choice and difficulty of tasks matter, and ten tasks are too few to support a sweeping ranking.

Now include the effort spent on failures as well as successes:

Minutes spent per successful task
    = total minutes spent on all attempts / successful tasks
Hypothetical comparison, not measured model performance
ConfigurationTasks completedTotal time, including failed attemptsMinutes spent per success
A8 of 1042 minutes42 / 8 = 5.25
B9 of 1075 minutes75 / 9 ≈ 8.33

B completes one more task in this invented example, but requires more total time. That tradeoff could be worthwhile if the additional task is important. A could be more useful for frequent, low-stakes edits. You need both columns to make the choice. If no task succeeds, report zero successes; the time-per-success ratio is undefined.

For this example, total time means sequential elapsed time from each submitted request until success or the time limit, including retries and review within that attempt. Record active human assistance separately. This prevents a fast model that needs constant correction from appearing equivalent to a setup that works with little supervision. Also inspect the result task by task: a higher aggregate score can hide failure on the particular kind of change you need.

A closer look: why a time budget changes the comparison

The resource-budget idea in SWE-Effi can be explored with this simplified, original example. Give each of three tasks at most ten minutes. Suppose two succeed after two and eight minutes, while the third fails. Define R(t) as the fraction of all three tasks successfully completed within t minutes. It is zero before two minutes, one-third from two to eight minutes, and two-thirds from eight to ten minutes. All time values in the calculation are in minutes.

Mean success fraction over the budget
    = area under R(t) / 10 minutes
    = [(6 × 1/3) + (2 × 2/3)] / 10
    = 1/3

The final success rate is two-thirds, but the average across the available budgets is one-third. The second measure rewards completing useful work earlier. This is a teaching example of a budget curve, not a reproduction of the paper's implementation or a measured model result. It also does not charge directly for time wasted on the failed task; the total-time record above still matters. Choose the measurement that answers your actual constraint.

[OPINION] I would choose the smallest comparison that resembles my work, keep the failures visible, and make the decision from that record. A model that saves me ten seconds generating an answer but costs me ten minutes repairing it has not saved time.

When a task fails, check what actually failed

A failed task does not immediately tell you to download a different model. Read the output and inspect the change. Did the model misunderstand the requirement, run out of room to finish its answer, miss a relevant file, or fail to use a tool?

Observations that help choose the next change
What you observeWhat to investigate
A complete patch violates a requirement.The instruction, relevant examples, and the model's reasoning about the code. Inspect the failing test.
The answer ends halfway through the patch.The output limit and the response's stop information.
The model cannot use information from a supplied file.Whether the application actually included that file and retained it in the request.
A file-reading or test command is repeatedly rejected.The application’s tool support, requested argument format, and returned error.
The setup is correct but each answer takes too long.The separate timing and hardware questions in the bandwidth article.

The amount of text available to a model at once is its context. Allocating more context may help when the work needs more source material, but it also changes memory requirements. Ollama documents how to inspect allocated context and processor placement with ollama ps. Use the effective setting shown by the running software, rather than assuming that the model's advertised maximum is what your application is using. [4]

Change one relevant setting at a time and repeat the same task. Keep the detailed memory calculation in Why a Longer Chat Needs More Memory, the speed investigation in Why a Model Can Fit and Still Feel Slow, and repeated action errors in Fix the Tool Loop Before You Replace the Model.

Start with two candidates and one useful task

Choose two models that your software supports and that can run on your machine. Give each the same small change and check the result. Save the model name and exact downloaded version, its quantization, the application and version, relevant settings, starting files, request, checks, elapsed time, and interventions. Then add a few different tasks before drawing a broader conclusion.

The first result you need is a working comparison you can repeat. It will show you which candidate deserves more testing and which part of the setup needs attention.

Give Your Coding Model Room to Finish the Job

Compare completed coding tasks, inspect the serving configuration and choose candidates without confusing leaderboard scores with local results.

By Sundog

7 September 2026

Make a coding agent useful

The first patch looks sensible. Then the agent retries a tool call, spends another minute thinking and loses the file it was meant to fix. I want the change finished before I start admiring the model. A leaderboard gives me candidates; the unfinished job gives me an investigation.

This article starts with a local coding model already running. Three parts of the setup matter: the model proposes text and actions; the runner loads and executes it; the agent application supplies files, tools and the conversation it retains. A chat template tells the runner how to format that conversation for the model. Support for tool calls depends on the model and template as well as the application. [1]

Start with one change you can judge

Use a small task in a disposable copy of a project. For example: make a filename filter accept both .CSV and .csv, while preserving its other behavior. Prepare an uppercase case, a lowercase case and an unrelated extension. This is an invented test task; no model results are being reported.

Give each run the same starting files, instruction and checks. Inspect the actual diff and the outcomes. A confident summary can overlook whether the unrelated extension is still rejected. Check that behavior yourself.

A controlled comparison for a model with a supported effort control
Keep fixedChangeRecord
Artifact, runner, template, context, tools, task and timeoutDefault effort versus one documented lower settingChecks passed, retries, tool failures, truncation and elapsed time

Reset the project copy and start a fresh conversation for each run. If your model or application does not expose a supported effort control, do not invent one. The same experiment can compare two documented context settings instead, holding effort fixed. Change one factor and keep the first result available.

[OPINION] I would try a small configuration change before downloading another promising model. If a lower effort setting finishes the same checks sooner, it earns another trial. If it retries more often and takes longer, the shorter individual answer has bought me nothing.

Context, output and reasoning are different controls

Context holds the request and the content the application retains. An output limit constrains generation. A model-specific reasoning effort or budget changes its supported thinking behavior. These controls interact, but there is no universal conversion from an effort label into gigabytes. Qwen3.8's serving instructions also warn that reducing effort can increase retries and total latency or token use. [2]

llama.cpp exposes context, parallel slots, fitting and reasoning controls separately. Changing a reasoning budget need not release a cache already reserved for the session. The context and slot allocation may matter more to memory. Inspect the effective configuration and the response's stop information, then check whether the task finished. [3]

Let the first observation choose the next check
ObservationInspect before changing models
Answer stops before producing the patchOutput limit, stop/finish information and the actual task result
Files or earlier instructions disappear from useRetained prompt, effective context and truncation
The same tool call fails repeatedlyArgument schema, template and the error returned to the model
Lower effort takes longer overallRetries and completed-task time, not only one generation

For Ollama, ollama ps shows loaded models, allocated context and processor placement in current versions. For llama.cpp, use its startup record and server controls. These are ways to inspect the running configuration; they do not translate one application's effort setting into another's. [4] [3]

A candidate screen belongs after the task

The following examples show what useful model evidence looks like. I have not tested these candidates on local hardware; the list illustrates evidence to collect before a comparison. A named artifact matters because two publishers can produce different files under the same quantization label.

OpenAI's gpt-oss-20b card reports about 21B total and 3.6B active parameters and uses MXFP4 for its evaluations. The artifact above is a concrete download from ggml-org. The publisher's 16 GB statement gives us a documented starting point. Each context and application still needs its own fit check. [5] [6] [7]

Qwen3.8-27B's configuration repeats three linear-attention layers followed by one full-attention layer. A conventional full-attention KV formula applied to every layer gives the wrong budget; the runner also needs its recurrent state. llama.cpp implements hybrid memory accordingly. [8] [9] [10]

Qwen3-Coder-Next's named artifact exceeds a single 24 GB card before cache and runtime allocations. More cards, unified memory or CPU offload change the capacity question and the performance question together. The bandwidth article explains why more total memory does not automatically make one session faster. [11] [12]

Why I would not turn the smaller candidate into an easy recommendation

Ornith-1.5 9B's owner supplies a Q4_K_M artifact of 5,780,090,816 bytes, small enough to investigate for a constrained setup. That does not establish a usable context length on an 8 GB card. In the September 6 source check, the Hub metadata said mit while the linked license endpoint returned 404. Resolve the terms with the publisher before a deployment that depends on them. [13] [14] [15]

If you already have a smaller model that loads and completes simple edits, use it for the first comparison. A tested 8 GB winner remains an open question here.

A reported score brings its setup with it

OpenAI reports 60.7 on SWE-bench Verified for gpt-oss-20b at high effort. NVIDIA's Nemotron comparison reports 52.44 for GPT-OSS 20B under its evaluator. Those unlike setups do not isolate the harness as the sole cause of the difference. Keep a published coding benchmark, a broad intelligence index and your own task comparison distinct. [5] [16] [17]

A benchmark can nominate the next candidate. Your small repeatable task tells you whether that candidate works with your files, tools and time budget. Repeat with a few different changes before treating one success as a general result.

Keep the configuration that finished the work

Save the model revision and filename, runner build, template, effective context, output limit, effort setting, task checks, retries and elapsed time. For a memory problem, continue to the context calculation. For a repeated action error, follow one tool call around the loop.

I want a finished change and enough of a record to repeat it after a week spent on something else. That is a model comparison worth keeping.

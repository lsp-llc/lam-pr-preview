5 minutes · zero to running

From zero to running

Every model on this site can be running on your machine in under five minutes. Here's the opinionated path most people take — and the eight tools worth knowing.

Local AI is simpler than it looks. Four steps below get you from nothing to chatting with a real LLM on your own hardware. No accounts or API keys are required for the local setup itself.

The Path

Four steps. Five minutes.

Click any command to copy it. Each step builds on the previous one — start at #1 and stop whenever you have what you need.

Security note: terminal commands and install scripts run on your own machine. Verify the source, inspect scripts before executing them, and use backups or an isolated environment when appropriate.

1
Install Ollama
One installer, all platforms. Handles model downloading, GPU detection, quantization, and an OpenAI-compatible API on localhost:11434. The single dependency for the rest of this guide.
curl -fsSL https://ollama.com/install.sh | sh
Or download from ollama.com for Windows/Mac.
2
Pull your first model
One command downloads and runs it. Ollama auto-selects the best quantization for your hardware. Llama 3.2 3B is a good starter — small, fast, and still very capable.
ollama run llama3.2:3b
~2 GB download. You're chatting in under a minute.
3
Add a web UI
Ollama's CLI works, but a web interface makes it actually enjoyable. Open WebUI is the community standard — ChatGPT-like with multi-user, document upload, RAG, web search, and plugins.
docker run -d -p 3000:8080 --add-host=host.docker.internal:host-gateway ghcr.io/open-webui/open-webui:main
Open localhost:3000. ChatGPT-like interface, your machine.
4
Scale up
Ready for more? Pull bigger models, add RAG with your documents, or set up image/video generation. Browse the catalog to find what fits your GPU.
ollama pull qwen3:32b
For 24GB GPUs. Or hit the model index to compare options.

Choosing a Runtime

Ollama or LM Studio: which should a beginner start with?

Start with LM Studio if you want a working chat window today and would rather not open a terminal. Start with Ollama if you are comfortable in a terminal, or if you already know you want other tools talking to your model over an API. Most people who stay with local AI end up running both.

LM Studio is a desktop application with a built-in model browser: search, click download, start chatting, without ever choosing a quantization or a file path. It is well optimized for Apple Silicon, it supports MCP tools, and it can expose a local API server. The tradeoff is that it is a graphical app, excellent at getting one person chatting on one machine and less natural as the always-on engine behind other software.

Ollama is a command-line tool and a background service. It downloads models, picks a sensible quantization for your hardware, and serves an OpenAI-compatible API on localhost:11434. That API is why Ollama sits underneath so much else on this site: Open WebUI, AnythingLLM, and most of the agent frameworks in the CLAWS catalog expect exactly that endpoint. It runs on llama.cpp, so it uses the same GGUF files everything else does.

  • LM Studio first on a Mac, or if the phrase "install script" makes you want to close the tab.
  • Ollama first if you want a web UI in front of your model, if you will wire a model into an editor or an agent framework, or if the machine is headless.
  • Both, once you know you are staying. LM Studio is a good model browser and scratchpad; Ollama is a good service.

Neither choice locks you in. Both run GGUF quantizations of the same models, so switching means re-downloading a file, not relearning the field.

The Whole Loop

How do you run AI models locally as a beginner?

Install a runtime, download one small model, and talk to it. That is the whole loop, and on normal broadband it takes about five minutes. The four-step path at the top of this page is the version most people follow; this is what is happening underneath it.

A local model is a file plus a program that reads it. The file is the weights, usually GGUF format, usually a few gigabytes. The program is the runtime: Ollama, LM Studio, or llama.cpp. The runtime loads the weights into memory, ideally your GPU's VRAM, and generates text one token at a time. Nothing leaves your machine, and after the download nothing needs an internet connection.

Your hardware sets the ceiling, not your skill. The one number that decides what you can run is how much VRAM your GPU has, or on an Apple Silicon Mac, how much unified memory the machine has. A model that fits in VRAM feels responsive. A model that does not fit gets split between GPU and system RAM, and gets slow in a way no setting will fix.

Quantization is how you make a model fit. Every VRAM figure on this site assumes Q4_K_M, the community default, which stores each weight at roughly 4.8 bits instead of 16 and stays close to full quality. Ollama picks for you, so you can start without understanding it, and the quantization guide explains the trade once you outgrow the default.

Start smaller than you think you need. A 3B model that answers instantly teaches you more in the first hour than a 32B model that takes a minute per reply.

The Ladder

Your first three models

Pull these in order. Each is in the catalog with full details, and each VRAM figure below is the catalog's own at the site's default quantization.

1. Llama 3.2 3B, roughly 1.5 to 3.6 GB, 128K context, Meta Community license. The model the four-step path uses, and the right first pull for almost everyone: a two gigabyte download, runs on effectively any GPU made in the last several years, and acceptable on CPU. Its job is to prove your setup works.

ollama run llama3.2:3b

2. Qwen3 8B, roughly 6 to 7 GB, 128K context, Apache 2.0, tool use supported. Your first genuinely capable daily driver. It fits comfortably on an 8 GB card, it is permissively licensed, and it supports tool calling, which agent frameworks need. On 8 GB of VRAM this is your ceiling model rather than your starter.

ollama pull qwen3:8b

3. Phi-4 14B, roughly 11 GB, 128K context, MIT. The step up, and the first model here that needs real hardware: 12 GB is tight, 16 GB is comfortable. Unusually strong at reasoning and math for its size, and MIT licensing makes it the least encumbered option in its class. Qwen3 14B lands in the same place at roughly 10.7 GB under Apache 2.0.

ollama pull phi4:14b

Two additions once those work. Add nomic-embed-text (under 1 GB) when you want the model to answer questions about your own documents, because retrieval needs an embedding model alongside the chat model. On a 24 GB card, Qwen3 32B at roughly 22 GB is the natural end of this ladder, and what Recommended Stacks builds its 24 GB configuration around.

No Graphics Card

Can you run an LLM locally without a GPU?

Yes. Every runtime on this page runs on CPU alone, and llama.cpp was built to do exactly that. The catch is speed: with the model in VRAM, practitioners generally report 15 to 50 tokens per second on consumer GPUs, and when the model has to run out of system RAM instead, that can fall to roughly 1 to 2 tokens per second. Those are reported ranges, not measurements taken on this site.

CPU-only inference is usable if you match the model to the situation. It works for short prompts, for batch jobs you are not watching, for classification and extraction over a queue of documents, and for anything where a fifteen second answer is fine. It does not work for interactive chat with a large model, or for coding assistance where you are waiting on the cursor.

The memory math does not change when you drop the GPU, it moves. A model needs the same total space whether that space is VRAM or system RAM, so a model listed at 6 GB still wants roughly 6 GB free, plus room for your operating system. Check free RAM, not installed RAM.

Worth trying on a CPU-only machine, all from this site's catalog:

  • SmolLM2 (135M / 360M / 1.7B), 0.3 to 1.5 GB, Apache 2.0. The smallest thing here that still holds a conversation.
  • Llama 3.2 (1B / 3B), 1.5 to 3.6 GB, 128K context. The 1B is the realistic CPU chat option.
  • Qwen3 (0.6B / 1.7B / 4B), 1 to 4 GB, Apache 2.0, with tool use.
  • Phi-4-mini (3.8B), around 3 GB, MIT, strong for its size on structured tasks.
  • Moonshine (Tiny / Base), under 0.5 GB, if what you want is speech to text rather than chat.

One exception: Apple Silicon Macs have no discrete GPU but are not CPU-only machines. Unified memory is shared between CPU and GPU, so a 32 GB or 64 GB Mac holds models that would need a professional card on a PC. Size against total unified memory instead.

When It Goes Wrong

Troubleshooting your first run

Six failures account for most first-day frustration. All of them look like a broken install and none of them are.

The model downloaded, then the answers crawl

Not a bug. The model did not fit in VRAM, so the runtime split it between GPU and system RAM. Offloaded layers run roughly three to ten times slower than layers on the GPU, so a half-offloaded model is dramatically slower, not slightly slower. The fix is a smaller model or a lower quantization, not a setting.

It will not load at all, or it crashes on load

Same cause, further along: the model plus its overhead exceeded what was available, and the runtime gave up instead of degrading. Budget roughly 1.2 to 1.5 times the stated model size to cover KV cache, activations, and overhead. And remember your display is already using VRAM. A 12 GB card driving two monitors does not have 12 GB free.

Something else is already using the port

Ollama serves on port 11434, and the Open WebUI container publishes on port 3000. If either is taken, the service refuses to start or the browser shows something unrelated. Port 3000 is the default for half the web tooling in existence, so publish the UI elsewhere by changing the left-hand number in the Docker port mapping. If port 11434 is occupied, find out what holds it before reassigning it, because the answer is often a second copy of Ollama already running fine.

It worked for short prompts, then died on a long document

Context length is the hidden VRAM cost. The KV cache grows with conversation length, so a session that started comfortably can run out of memory ten messages later, or the moment you paste in a long file. The quantization guide carries the per-model-size figures for that cost. A model advertising a 128K window will not give you 128K on a small card: the window is a property of the model, affording it is a property of your hardware. Reduce context until the session is stable. In the Ollama REPL, /set parameter num_ctx 4096 sets it per session, and OLLAMA_CONTEXT_LENGTH sets a service default. One catch: a num_ctx value baked into a model's Modelfile overrides that environment variable, so a model built with its own context length keeps it until the Modelfile changes.

The quantization tags are confusing

ollama pull llama3.3 gives you Q4_K_M, the community default, and for most people that ends the decision. Confusion starts with tags like 70b-instruct-q8_0 or 70b-instruct-q2_K. The number is bits per weight, so q8_0 is closer to the original than q4_K_M, which is closer than q2_K, and higher quality costs VRAM in roughly the proportion you would expect. Do not chase a higher quantization of a model that barely fits: a smaller model at a higher quantization usually beats a larger model at a lower one, especially for code.

The web UI cannot see Ollama

Open WebUI runs in a container, and inside that container localhost means the container, not your machine. That is the purpose of the --add-host=host.docker.internal:host-gateway flag in the install command above, and it is the flag people drop when retyping from memory. If the UI loads but shows no models, check that flag first, then confirm Ollama is running by requesting localhost:11434 on the host.

Chat Speed Follows the Corridor

Updated: August 2026 · Dated decision 2026-08-20

Batch-1 decode on a desk GPU walks the memory bus. Shopping more TFLOPS on the same GDDR bus leaves the token arrival rate where it was.

Plate · the librarian and the corridor

Picture the GPU as a librarian and the memory bus as the only corridor between the stacks and the reading room. Every time a visitor asks for the next word, the librarian must walk the entire collection down that corridor: every shelf of weights, plus the growing cart of notes already taken. The reading room is vast. The corridor is narrow.

A faster reader at the far end of the same corridor still waits on the cart. That is batch-1 decode. The advertised teraflops are the reading room. The published gigabytes per second are the corridor. Chat speed is the trip, repeated once per token, and the trip is what you buy.

The stacks stay long when the reader is quicker. They shorten when you compress the books or skip a wing. Those choices sit apart from a faster GPU on the brochure.

Where the Metaphor Bends

A corridor is a single width. Real silicon is messier. Peak bandwidth is a datasheet number. Kernels, cache hierarchy, and allocator noise mean you never walk it at 100 percent. The cart of notes (the KV cache) grows with context, so the second half of a long reply is a heavier trip than the first word. Unified memory on Apple silicon is a different building: one floor plan shared with the operating system, beside a discrete GDDR annex.

The metaphor also fails on the first pass through a long prompt. Prefill is a class arriving at once. The same shelves are read. The work is reused across hundreds or thousands of tokens, and the reading room can finally fill. That is the compute-bound exception. First-token latency and chat tokens-per-second are different shopping questions.

Three more bends, named here so they do not sneak in later as magic. A batch of visitors shares one trip and intensity rises. An assistant who guesses the next line lets the librarian check a handful of words in one walk (speculative decoding). A library that only opens two wings per request still stores every wing (mixture of experts). Speed and occupancy part company. The rest of this page is the arithmetic those bends sit on.

On 20 August 2026 this site treats desk-GPU chat speed as a bandwidth ceiling. The formula below is calculated from vendor-published memory bandwidth and a stated weight footprint. Use it to refuse a purchase that leaves the corridor unchanged.

The decision. Buy memory bandwidth (and the VRAM to keep the weights on that bus) for interactive batch-1 decode. Buy compute for prefill-heavy work: long prompts, retrieval dumps, fill-in-the-middle. A card that advertises more TFLOPS on a similar GDDR corridor will not raise batch-1 tok/s in proportion to the brochure.

What is the tokens-per-second ceiling for batch-1 decode?

Once the weights fit in VRAM, each new token is a memory stream. The GPU must read the parameters (and the KV cache) from device memory into the compute units. The arithmetic update is small. Pope, Douglas, Chowdhery and colleagues put the same split in serving language: at small batch the time to load weights dominates. At large batch and long sequence, KV traffic takes over[2]. A desk chat session is the small-batch case.

That produces a hard ceiling you can write on a whiteboard:

tokens/s ≲ memory_bandwidth_bytes_per_s / bytes_moved_per_token Calculated ceiling · weights streamed each step, plus KV · not a measured 4090 run

Bytes moved per token is, to first order, the resident weight file plus the KV bytes you reread at this context length. For a planning 8B at Q4, the site’s quantization table prices Q4_K_M at 4.8 effective bits, so 8 × 4.8 / 8 = 4.8 GB of weights, which we round to ~5 GB when talking in the same units as a spec sheet[11]. Divide published bandwidth by that number and you have an upper bound. Real llama.cpp or Ollama runs land at a fraction of it. Imperfect bus utilization, kernel launch, and the KV term eat the gap. The stack builder already labels its tok/s column as a theoretical upper bound from this model.

Capacity decides whether the model runs on the GPU at all. That is the VRAM guide. Bandwidth decides how fast the tokens arrive once it does. Confusing the two is how people buy a faster SKU and keep the same chat pace.

How does the roofline model place decode under the memory roof?

Williams, Waterman and Patterson’s 2009 Roofline paper is the visual: attainable performance is the minimum of peak FLOP/s and bandwidth times operational intensity[1].

peak performance ≈ min( peak_FLOP/s , bandwidth × operational_intensity ) Williams, Waterman, Patterson · CACM 2009 · DOI 10.1145/1498765.1498785

Operational intensity is FLOPs per byte of DRAM traffic. For a weight matrix applied to a single token, you pay about two FLOPs per parameter (multiply-add) and you read each parameter once. Intensity then collapses to 2 / bytes_per_weight. At FP16 that is 1 FLOP/byte. At Q4_K_M (~0.6 bytes/weight) it is about 3.3 FLOP/byte. Those are low-intensity kernels. They hit the slanted roof.

NVIDIA’s Ada whitepaper lists the GeForce RTX 4090 at 82.6 FP32 TFLOPS and 1008 GB/s of memory bandwidth[3]. The ridge point is 82.6e12 / 1008e9 ≈ 82 FLOP/byte. Batch-1 decode at 1–4 FLOP/byte sits an order of magnitude to the left. Tensor-core peaks are higher still, which only moves the flat roof up and leaves decode on the slope.

Prefill walks the other way. A prompt of length S reuses the same weights across S tokens, so intensity scales with S. At S = 512 and Q4, a back-of-envelope 512 × 3.3 ≈ 1,700 FLOP/byte is already past that 82 FLOP/byte ridge. The kernel can saturate the ALUs. A machine that feels merely fine in chat can still chew a long system prompt. First-token time is the wrong number when you are shopping for streaming replies.

What is the calculated decode ceiling on published GPU bandwidth?

The table uses vendor-published peak bandwidth. Weight traffic is the 5.00 GB planning figure for an 8B Q4 (the 4.8 GB k-quant math, rounded). The last column is bandwidth / 5.00e9. It assumes the entire weight file moves every token and that KV is zero. Both assumptions make the number optimistic.

All tok/s figures in this table are calculated, not measured. Ceilings from published GB/s ÷ 5.00 GB. This article took no 4090 throughput run.
Device Published bandwidth Source Ceiling at 5.00 GB weights
GeForce RTX 4090 1008 GB/s NVIDIA Ada architecture whitepaper[3] 202 tok/s
GeForce RTX 4080 716.8 GB/s NVIDIA Ada architecture whitepaper[3] 143 tok/s
GeForce RTX 3090 936 GB/s NVIDIA Ampere GA102 whitepaper[4] 187 tok/s
GeForce RTX 3060 12 GB 360 GB/s NVIDIA GeForce News Q&A[5] 72 tok/s
Apple M1 68.25 GB/s AnandTech M1 memory-bus calculation[6] 14 tok/s
Apple M1 Pro up to 200 GB/s Apple Newsroom / Support spec[7] 40 tok/s
Apple M1 Max up to 400 GB/s Apple Newsroom / Support spec[7] 80 tok/s
Apple M2 100 GB/s Apple Newsroom (M2 announcement)[8] 20 tok/s

Read the 4090 and 3090 rows together. Ampere lists the 3090 at 35.6 FP32 TFLOPS and 936 GB/s[4]. Ada lists the 4090 at 82.6 FP32 TFLOPS and 1008 GB/s[3]. Compute more than doubles. The corridor widens by 1008 / 936 ≈ 8 percent. The calculated weight-only ceilings move from 187 to 202 tok/s. Ada spent the process node on ALUs and caches. The memory bus stayed in the same class. If your workload is batch-1 chat, you bought the reading room. I would refuse a 3090-to-4090 jump sold as a chat-speed doubling on an 8B that already fits. The calculated corridor moves 8 percent.

The 4080 row is the intra-generation check. Same Ada family, 716.8 GB/s against 1008 GB/s: a 29 percent narrower corridor and a 143 vs 202 calculated ceiling. If two cards share a memory technology and a similar bus width, chat will not follow the CUDA-core count.

The 3060 12 GB row is the budget reality. 360 GB/s is a bit over a third of the 4090. The calculated ceiling is 72 tok/s on the same 5 GB file, and only if the 8B actually fits with context, which on 12 GB it can at Q4 with a modest window (VRAM arithmetic). People who call a 3060 slow at 7B and a 4090 fast at 7B are naming the bus.

Apple’s published unified-memory figures explain the Mac stacks on this site. M2 at 100 GB/s is a 20 tok/s calculated ceiling on the same 5 GB file. M1 Max at 400 GB/s is 80. The recommended stacks already warn that M-series generation is memory-bandwidth-bound and that a 64 GB Mac is a capacity play. A 70B at Q4 that finally fits in unified memory still walks a 100–400 GB/s corridor. The 1008 GB/s GDDR6X annex is a different invoice.

Do not quote these ceilings as “a 4090 does 202 tok/s.” They are arithmetic on a datasheet. The stack builder applies an efficiency factor and still calls the result theoretical. Community benches vary with context, backend, and whether the run is decode-only. This page will not invent a 4090 measurement it did not take.

How much does the KV cache move the ceiling?

Pope et al. treat weights and KV as the two large HBM residents that must be transferred each forward pass[2]. At short context the weight term wins. At long context the cache can rival it. That is the same third term the VRAM guide charges for occupancy. Here it is a bandwidth term.

A concrete calculated example. Meta’s Llama 3 8B config uses 32 layers, 8 key/value heads, and a 128-wide head[9]. For FP16 KV, bytes per token of context are:

2 × 32 layers × 8 KV heads × 128 dim × 2 bytes = 131,072 bytes / token of context Calculated from the published 8B config · FP16 cache · not a measured trace

At 4,096 tokens that is 512 MiB. Add it to the 5.00 GB weight file and the 4090 weight-only ceiling of 202 tok/s becomes 1008e9 / 5.50e9 ≈ 183 tok/s, still calculated. At 32,768 tokens the cache is 4.00 GiB and the same formula gives 1008 / 9.00 ≈ 112 tok/s. The card did not get slower. The cart got heavier. Grouped-query attention is why that cache is 8 heads. Multi-head at 32 would have quadrupled the KV term.

Two operator consequences. First, a decode-speed complaint that appears only after the context fills is often KV traffic. Second, quantizing the cache (when the runtime offers a real flag for it) shrinks bytes moved the same way Q4 shrinks weights. The quantization guide already carries the quality caveat for weights. This page does not invent a cache-quant flag. Check the runtime you actually run.

When do TFLOPS matter? On prefill.

Prefill is the exception named in the decision. A long prompt is a batched matrix multiply against the same weights. Intensity rises with prompt length. The roofline can hit the flat roof. That is where 82.6 TFLOPS versus 35.6 TFLOPS is allowed to show up: time-to-first-token on a 4K or 32K paste. Streaming pace of the reply stays on the bus.

A compute-heavy card helps you swallow the prompt. A bandwidth-heavy card helps you talk. RAG pipelines that dump retrieved chunks into the window are prefill-bound on the first token and bandwidth-bound on every token after. If your day is “paste a repo, wait, then skim a short answer,” shop the ALU. If your day is “small prompt, long streamed answer,” shop the bus. Most interactive local chat is the second day.

Offloading is a speed cliff. Once layers spill to host RAM you have left the 360–1008 GB/s device corridor for a CPU memory controller measured in tens of GB/s. The VRAM guide already records the occupancy failure. The bandwidth reading is the same failure in motion: the librarian is now walking to another building.

How do batch, speculative decoding, and MoE change intensity?

Three legal ways to climb off the worst part of the slope. The list is batch, speculative decoding, and MoE. A new SKU with more cores on the same GDDR stays off it.

1. Batch: share the weight trip

If two independent sequences need the next token, you still read the weights once and apply them twice. Intensity roughly doubles. Pope et al. say the obvious serving consequence: at large batch, weight load is amortized and KV can dominate[2]. On a desk this is the difference between one chat window and a small local server with a few concurrent clients. The token simulator is a single-stream feeler. It will not show you the batch win. The cost is latency isolation. You are no longer optimizing for one person’s next word.

2. Speculative decoding: check several words per walk

Leviathan, Kalman and Matias (2023) show that a cheaper draft model can propose several tokens that the large model then verifies in one forward pass, with 2×–3× wall-clock gains on their T5-XXL measurements and no change to the output distribution[10]. Intensity rises because the large model’s weight stream is reused across the draft prefix. The desk catch: you now hold a draft model as well, and accept-rate depends on how easy the next tokens are. It is a real method with a paper. The 202 tok/s ceiling does not get a free multiply.

3. Mixture of experts: walk fewer shelves, store every wing

Mixtral 8x7B is the cited open example: 47B total parameters, 13B active per token, because a router picks two of eight feed-forward experts at each layer[12]. Compute and, if the runtime actually skips inactive experts, weight traffic follow the active set. Occupancy still holds every expert. The VRAM guide already prices that floor space. If llama.cpp (or whichever backend you run) streams only the chosen experts, the denominator in the ceiling shrinks and tok/s can rise toward a dense 13B. If a naive path touches every expert tensor, you paid the VRAM tax and kept the 47B walk. Confirm the path you are running.

MoE buys a larger library to get a shorter trip, provided the librarian is allowed to skip closed wings. The 4090-vs-3090 TFLOPS mistake buys a larger reading room and keeps the same hallway.

What should you actually buy, given this ceiling?

Start from fit. Then read the bus. Then weigh compute.

  • Fit first. A model that spills to host RAM has left the GPU corridor. Size weights, KV, and overhead with the VRAM guide and the workstation builder before you argue tok/s.
  • Then read the spec sheet’s memory line. 1008, 716.8, 936, 360, 400, 200, 100, 68.25. Those are the published numbers this page is willing to divide by. A card whose marketing lead is more CUDA cores or more TFLOPS on a similar GB/s figure is a prefill upgrade.
  • Then decide if your day is prefill. Long-context coding and retrieval dumps spend real time in the compute-bound region. That is when Ada’s 82.6 TFLOPS versus Ampere’s 35.6 is a reason to pay. Streaming tok/s will not scale 2.3×.

Worked refusal: upgrading a 3090 to a 4090 to “double chat speed” on an 8B that already fits. The calculated corridor moves 8 percent. Keep the 3090, or spend the money on capacity you do not have (a second card, a 70B that does not fit, unified memory for a model the 24 GB card cannot hold). Worked acceptance: replacing a 3060 12 GB (360 GB/s) with a 4090 (1008 GB/s) on a model both can hold is a calculated 2.8× ceiling move, and the 4090 also buys context headroom. That purchase can be about speed.

Mac buyers already live this split. The stack notes prefer MLX and tell you discrete-GPU tok/s will not appear. Unified memory is how a 64 GB M-series holds a 70B. 400 GB/s is why it will not feel like a 4090 while it talks. Capacity and corridor are different invoices.

Which llama.cpp flags actually touch this picture?

Only flags that exist in the current llama.cpp server README are worth naming here. -ngl / --n-gpu-layers (also --gpu-layers) sets how many layers live in VRAM: exact count, auto, or all[13]. That is a fit flag. It decides whether you are on the device corridor or walking to host memory. It does not widen the bus. -fa / --flash-attn takes on, off, or auto (default auto)[13]. FlashAttention changes how attention traffic is staged. The MLP weight stream stays a bandwidth walk. If a blog tells you to pass a flag this README does not list, treat that as a different program.

The operator habit this page wants: before you change cards, confirm -ngl has the whole model resident and that you are looking at decode tok/s. The token simulator is there to calibrate what 5, 25, and 80 tok/s feel like. The ceiling table above tells you which of those bands a given bus can even reach on a 5 GB file.

How this sits next to the rest of the site

The VRAM guide answers “does it fit.” The quantization guide answers “how many bits per weight,” which is the denominator of intensity and the size of the file you stream. The stack builder already divides published bandwidth by model size and labels the result a theoretical upper bound. The recommended stacks already call M-series generation bandwidth-bound. This page is the missing essay: why those labels exist, and why the next GPU on the same GDDR generation is the wrong medicine for a slow chat.

If you want a feel for the stream, use the token simulator. If you do not own the card yet, the workstation builder turns a VRAM target into parts. Neither tool invents a 4090 bench for this article.

Frequently asked questions

Why is local LLM chat speed limited by memory bandwidth?

At batch-1 decode the GPU streams nearly the whole weight file, plus the KV cache, for every new token. Arithmetic intensity is a few FLOPs per byte. Roofline then says the attainable rate is bandwidth times that intensity, which rewrites as tokens/s ≈ bandwidth / bytes_moved_per_token[1][2]. Extra TFLOPS sit unused on the flat part of the roof.

Will a GPU with more TFLOPS make local chat faster?

Only if it also widens the memory corridor. The 4090 versus 3090 pair is the dated example: 82.6 vs 35.6 FP32 TFLOPS, 1008 vs 936 GB/s[3][4]. Compute more than doubled. The calculated 5 GB ceiling moved from 187 to 202 tok/s. Shop the GB/s line.

When do TFLOPS matter for local LLMs?

Prefill. A long prompt reuses weights across many tokens, intensity rises, and the kernel can hit the compute roof. First-token time on a pasted context is the compute-bound number. Streaming chat stays on the slope.

How do you estimate a theoretical tokens-per-second ceiling?

Divide vendor-published peak bandwidth by bytes streamed per decode step. For 8B Q4_K_M, weights are 4.8 GB by the site’s 4.8-bit rule, ~5 GB as a planning figure. On 1008 GB/s that is a calculated 202 tok/s if only weights move. Subtract nothing for software, then remember real runtimes are a fraction. Do not treat the result as a 4090 measurement.

Does a Mac with more unified memory generate faster?

More unified memory lets a larger model fit. Generation speed still tracks the published unified-memory bandwidth: 68.25 GB/s on M1, 100 GB/s on M2, up to 200 / 400 GB/s on M1 Pro / Max[6][8][7]. A 64 GB Mac that holds a 70B still walks the published Mac bus.

Does Mixtral’s 13B active set mean I only need 13B of VRAM?

No. Mixtral 8x7B exposes 47B parameters and uses 13B per token[12]. Occupancy follows the full set. Speed follows the active set only if the runtime skips inactive experts. Larger library, shorter trip, same floor space.

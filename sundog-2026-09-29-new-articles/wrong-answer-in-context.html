When Yesterday’s Wrong Answer Becomes Today’s Evidence

Follow how an early guess can survive later corrections, then separate the current facts from the conversation that accumulated around them.

By Sundog

29 September 2026 · 6 min read · Start here

You correct an assistant’s answer. A few messages later, the old answer turns up again, now woven into an explanation of the correction. The conversation contains the right information, but it also contains a convincing account of the wrong information.

That distinction matters when you use a local model for a running project, a document analysis, or a long technical conversation. Supplying a fact and getting the model to use it are different achievements. Recent research gives us a way to examine that gap without treating every failure as a shortage of model size.

I would start by asking what the model is carrying forward. A transcript preserves what people said. A dependable working record needs to preserve what is currently true, what remains uncertain, and which earlier statements have been replaced.

The history contains more than the user’s facts

Consider this original example. Three replacement parts cost £48 each. Shipping was first quoted at £24, then corrected to £12. The current total is 3 × £48 + £12 = £156. An earlier assistant response calculated £168 using the first quote.

A long chat now contains both numbers, two shipping charges, and an assistant’s explanation of the obsolete total. A fresh prompt containing only the current quantities is a different input from that transcript, even though both contain all the facts needed to calculate £156.

Illustrative example, not a model run. The answer follows directly from the current inputs.

The language model produces an answer conditioned on the available text, including its previous answers. We can write that as P(answer | current facts, history). This notation does not tell us which sentence controls the output. It reminds us that history is part of the input, rather than a trustworthy record that the model has already reconciled.

A wrong earlier answer can contaminate a later one

Same Evidence, Different Answers studies incomplete conversations and contamination from earlier replies. Its Table 2 reports a Qwen3-8B math evaluation on 103 problems: 90.3% accuracy with a clean prompt, 33.0% after an assistant-side wrong solution, and 63.1% with a user-side wrong-answer hint. The latter prompts differed in wording as well as speaker, so the gap does not isolate a pure role effect. [1]

The first difference is 57.3 percentage points: 90.3 − 33.0. That measures a change in accuracy for the tested conditions. It is neither a universal chance of failure nor proof that an assistant message always matters more than a user message. For that comparison, the wording would need to be held constant.

The authors’ training method, CCOPD, aligns a student receiving conversation history with a frozen teacher receiving complete evidence. It is a trained intervention, not an instruction you can reproduce by telling a stock model to forget. The practical lesson here is to test history contamination separately from whether the model can solve the clean task. [1]

A neat data structure can carry the wrong fact too

Earlier answers are one source of contamination. Conflicting retrieved material is another. A paragraph may say a device was released in 2024 while a compact structured record says 2023. Both can look authoritative; the compact one can be especially easy to reuse.

ConflictQA pairs textual passages with knowledge-graph evidence and introduces conflicts. On its 802-question non-complementary evaluation, Qwen3-8B exact match falls from 76.28% to 7.61% when the triples conflict with correct text, and to 52.44% when the text conflicts with correct triples. Those are benchmark-specific outcomes; evidence length, source type and format are not isolated from one another. [2]

The study also finds prompt and order sensitivity. Its proposed explanation-based approach is not uniformly helpful: Qwen3-8B improves under conflicting triples but worsens under conflicting text. A longer explanation cannot be assumed to resolve the conflict. [2]

That gives us two related questions, with different mechanisms: did the assistant inherit its own old conclusion, and did it favor the wrong external source? Combining the papers makes the engineering problem more visible. It does not establish that both failures have the same internal cause.

Compare a conversation with a current-state prompt

You can explore this on the local model you already use. The following is an original diagnostic design, not a reproduction of either paper. It needs two fresh chats and a problem whose answer you can determine independently.

In the first chat, provide only the current facts:

Three parts cost £48 each. The current shipping charge is £12.
Calculate the total. End with FINAL: followed by the amount.

In the second, first ask the same question with shipping at £24, then supply the correction:

The shipping charge has been corrected to £12.
The quantities and unit prices are unchanged.
Calculate the current total from those inputs.
End with FINAL: followed by the amount.

The first condition checks basic arithmetic. The second checks whether an answer survives a changed premise. If the clean prompt fails, you have not isolated a history problem. If the clean prompt succeeds while the correction fails, examine whether the model used the obsolete shipping charge, misread the update, or calculated incorrectly despite identifying the correct inputs.

To test the effect of an earlier wrong answer more directly, use a chat application that lets you edit or supply conversation messages. Insert the same obsolete sentence once as a user message and once as an assistant message. Keep the wording, facts and final question identical. Merely quoting an “assistant answer” inside a user message is a separate condition; it does not change that message’s actual role.

Keep your model, precision, chat template, output allowance and sampling settings fixed. Repeat on several independently checkable problems. A handful of examples can expose a failure and improve your workflow; it cannot establish the published error rate on your hardware.

Build a record the next answer can use

My proposed repair is to give the model a compact, explicit current-state record when a task has accumulated corrections. In the parts example, that record would contain quantities, current shipping, the superseded shipping value, and the rule that totals must be recalculated. It would not treat £168 as another independent piece of evidence.

There is a tradeoff. A fresh record can remove useful history along with the stale material. Preserve unresolved questions, important constraints and source identifiers. For a document conflict, include the revision or effective date that makes one source applicable; do not ask the model to choose merely because one entry is newer or more concise.

When the sources genuinely disagree and no authority rule resolves them, the useful answer may be conditional: “The total is £156 if the corrected quote applies; otherwise it is £168.” That is a different outcome from averaging the totals or picking whichever number appeared last.

[OPINION] I would rather spend a few lines making the current facts explicit than spend another thousand tokens asking an assistant to reconsider a transcript full of its own confident mistakes. The record should earn its place by changing the answer reliably. If it does not, the next step is a better fact-handling mechanism, not a more elaborate reminder.

Joules Per Token

Dated: 20 August 2026 · nameplates are envelopes, not measurements

Desk-GPU decode energy tracks bytes moved, not peak TFLOPS. A quiet 24 GB card generating all night can beat an API on electricity at high volume and lose on idle overhead at low volume.

Scientific Plate I · ad-free header

The Meter Under the Muse

The muse is the model that keeps talking after midnight. The meter is the only critic that cannot be flattered. This plate is a spine, not a proof: while a token is born, the board is paying for the trip the resident bytes take through memory. The poem stops at the header. The envelopes start below.

Where the metaphor bends · ad-free

Four places the picture fails

A muse-and-meter image is useful only if you know where it lies. A nameplate wattage is a cap, not the average draw of a llama.cpp decode loop. Prefill is not decode: one phase is compute-bound, the other walks memory. Idle hours are not generating hours. And a paper that measured A6000 and A100 boards is not a 4090 wall-meter log. Those four bends are the rest of this page.

This is a practitioner guide for people who already run, or are about to run, open-weight models on a desk GPU or a Mac Studio. It is dated 20 August 2026. The thesis is narrow: decode energy tracks bytes moved — the weight file plus the growing KV state — not peak TFLOPS. Prefill is the compute-bound spike. Every watt printed below was opened on a vendor page or in a paper that names its hardware. No joules-per-token figure on this page is a measurement of llama.cpp on a GeForce RTX 4090. If the average watts for that loop were not measured here, they are not invented here.

The only honest formula, and why this page will not finish it

A joule is a watt-second. For one phase of inference — prefill or decode — the unit you actually want is:

joules/token = (average watts in that phase) / (tokens per second in that phase)

That identity is not a model. It is the definition. If you know the mean board draw while the runtime is prefilling, and you know how many prompt tokens you processed per second, you have prefill joules per token. If you know the mean draw while it is emitting tokens, and you know decode tokens per second, you have decode joules per token. Mix the phases and you hide the spike behind the walk.

This site does not have a measured average-watt number for llama.cpp decode on a 4090, a Mac Studio, or anything else. NVIDIA's published Total Graphics Power is a cap, not that average. Apple's published Mac Studio "Max" is a whole-system wall figure under a compute-intensive test, not an LLM-decode measurement. Plugging either nameplate into the formula and calling the result "joules per token on your desk" would be an invention. The formula stays on the page. The fake product does not.

What you can do tonight, if you want a number that is yours: read average watts from a tool that actually samples the board or the wall during a decode-only loop, read tokens per second from the runtime for that same loop, and divide. Until you do that, you have envelopes and a mechanism, not a constant.

Why decode tracks bytes moved, not TFLOPS

A decoder that emits one token at a time, at batch size one, must stream the resident weights and attend over the key/value state it has already written. The arithmetic per weight is a handful of multiply-adds. The traffic is the quantized width of those weights plus the KV bytes that belong to the tokens already in context. Operational intensity — operations per byte of memory traffic — stays low. The card's published teraflop rating describes a different roof: the one you hit when the working set is reused hard enough that the arithmetic units stay busy. Batch-one decode is not that kernel.

Williams, Waterman, and Patterson's Roofline model (Communications of the ACM, April 2009, DOI 10.1145/1498765.1498785) is the picture for that split. A kernel either hits the flat compute roof or the slanted memory roof. The ridge is peak FLOPS divided by peak bandwidth. Sit left of the ridge and buying more TFLOPS does not buy you tokens. It buys you a nameplate that decode will not spend. This page uses Roofline for that geometry. It does not take a 2009 CPU paper as a joule measurement.

Resident bytes are the denominator of the speed ceiling, not a second thesis. At modest context the weight file dominates. As the conversation lengthens, KV grows and the walk gets heavier. That is why a long window feels slower on the same card that flew at 2K. The VRAM guide is how you decide whether the file plus the window still fit. This page is why the same bytes decide energy once they do: more bytes per token means fewer tokens per second on a memory roof, and joules per token move unless average watts fall as fast as throughput does.

The Stack Builder already prints tokens per second as a theoretical upper bound from memory bandwidth divided by model size at the selected quantization. This article will not invent a second bandwidth guide and will not link a page that is not on this site. The ceiling is conceptual:

tokens/s_ceiling ≈ published_bandwidth / resident_bytes_per_token
resident_bytes ≈ weight_file + KV_state

At Q4_K_M, 4.8 effective bits, the weight term is about 0.6 bytes per parameter. A 7B file is about 4.2 GB of weight traffic per decoded token before KV. A 32B file is about 19.2 GB. Those are file sizes, not joules. The 4090's published memory bandwidth is 1008 GB/s. The roof says you cannot decode faster than about 1008 divided by whatever resident bytes you are actually streaming. Real llama.cpp will come in under that roof. This page will not convert the roof into a fake joule by multiplying it by 450 W.

Prefill is compute-bound; decode is the long walk

Fernandez, Na, Tiwari, Bisk, Luccioni, and Strubell, "Energy Considerations of Large Language Model Inference and Efficiency Optimizations" (arXiv:2504.17674, 2025), opened for this article, decompose inference the way a desk operator should. Quote the mechanism, not their hardware as yours:

  • The prefill stage processes prompts in parallel and is typically compute-bound, achieving high GPU utilization.
  • The autoregressive decoding stage is typically memory-bound and leads to GPU under-utilization.
  • Decode energy intensity scales with sequence length because decode is sequential. In their controlled sweeps, decoding energy dominates the workload except at the shortest generations (classification, short summarization).

Their accelerators are named in the paper: NVIDIA RTX A6000, A6000 Ada, and A100 80GB PCIe, measured with NVML via CodeCarbon, on Llama-3.1 and Qwen-class models in PyTorch and vLLM. That is not a GeForce RTX 4090 and not a Mac Studio. This page takes the phase split and the dominance of decode on ordinary generation lengths. It does not take their joule totals, their 73 percent optimization figure, or their datacenter framing and reprint them as a desk-GPU result.

What a desk operator should do with that split is practical. A short prompt and a long completion spend almost all of the generating time — and, in Fernandez et al.'s geometry, most of the energy — in the memory-bound walk. A dumped repository and a one-line answer spend a surprising fraction in the compute-bound prefill spike. The 450 W and 145 W envelopes below are more plausible as brief prefill caps than as decode averages, because decode is the under-utilized phase. Using one number for both phases is how people talk themselves into a constant that does not exist.

Batching, continuous batching, and speculative decoding change utilization. Fernandez et al. show speculative decoding saving energy at small batches and costing energy at large ones, because the draft-and-verify extra work only pays when the target model was idle. Desk chat is usually batch one. Overnight evals do not have to be. Those are utilization knobs, not new nameplates.

Nameplates: two envelopes you can actually open

NVIDIA's GeForce RTX 4090 product page, opened for this article, is the consumer 24 GB card this site already treats as the desk sweet spot. The figures used here are Total Graphics Power 450 W, 24 GB of GDDR6X, and published memory bandwidth 1008 GB/s. TGP is a cap: the board is not allowed to exceed that budget under the vendor's thermal and power design. It is not a promise that llama.cpp decode sits at 450 W. The same page also prints an Idle Power of 19 W for a Founders / reference card left at the Windows desktop for ten minutes, and an Average Gaming Power of 315 W across 22 games. Neither of those is an LLM-decode measurement. They are listed so the 450 W row has company on the official table, and so idle tax has a published floor that is not 450 W.

Apple's "Mac Studio power consumption and thermal output (BTU) information" page (support.apple.com/en-us/102027, published 12 March 2025), opened for this article, is the whole-system envelope for a 2025 Mac Studio with M4 Max (14-core CPU, 32-core GPU, 36 GB unified memory, 512 GB SSD in the tested config). Apple prints Idle 6 W and Max 145 W. The notes on that page matter as much as the numbers: watts are measured from the wall and include power-supply and system losses; "Max" is a compute-intensive test that maximizes processor usage with no external peripherals; "Idle" is Finder open at default power-management settings; ambient was 20.2 °C. That is not an LLM-decode measurement. It is the honest Apple nameplate for the box. A decode loop will sit somewhere between 6 W and 145 W. This page will not guess where.

Decode on a memory roof is under-utilized by construction (Fernandez et al., on A6000/A100, mechanism only). Expect average decode watts to sit well below the 450 W or 145 W nameplate more often than not. Prefill can walk toward the cap for a short interval. If you need a planning bound, the nameplate is the bound on power, not a substitute for average watts in the joules-per-token formula.

Idle and always-on tax, without a fake per-token product

Two clocks still hide inside any daily energy number. The generating clock is the seconds the runtime is prefilling or decoding. The occupancy clock is the hours the machine is powered. Fernandez et al. are about the first clock. The Apple 6 W idle row and the NVIDIA 19 W idle row are about the second.

Arithmetic on a published idle, not on an invented decode watt:

Mac Studio M4 Max idle envelope: 6 W × 24 h = 0.144 kWh/day if the box never sleeps
RTX 4090 desktop-idle envelope: 19 W × 24 h = 0.456 kWh/day if the card stays powered at that floor

Those kilowatt-hours exist whether you emit a million tokens or ten. They are not joules per token until you divide by a token count you actually produced. At high overnight volume the occupancy term is a rounding error next to generating energy. At a handful of coding completions after dinner, occupancy is the bill. A quiet 24 GB card generating all night can beat an API on electricity. The same card left resident "so the first token is fast" can lose on idle overhead. That fork does not require a fabricated 4090 joules-per-token constant. It requires you to notice whether the machine was on.

Always-on tax is larger than the GPU row. Apple's 6 W already includes PSU losses for that idle test. NVIDIA's 19 W does not include the rest of a tower. This page leaves the unlisted watts unlisted. Your wall meter will not.

Powering down, or unloading the model so the driver can drop toward the published idle, is an energy decision. Leaving a 32B resident across an idle afternoon is also an energy decision. The token simulator will show you what slow feels like. It will not pay occupancy for you.

Operator call, 20 August 2026: local energy versus an API list price

Call. After the hardware is already on the desk, local energy wins against a public API list price when the day's tokens amortize occupancy and the generating phases are decode-heavy. It loses when the box is always on and the day's tokens are thin, or when the day is prefill-heavy and you were budgeting as if the memory roof were the whole story. The fork is occupancy and phase mix, not a slogan about electricity.

This page will not print a dollars-per-million-token API table. OpenAI's pricing page exists; other vendors publish list prices too. Those tables move, and a copied row that this article did not treat as a static primary source would be a fake table. Finish the comparison with two numbers you actually have: the rate on your utility bill, and the list price on the API page you pay.

If — and only if — you later measure average decode watts W and decode tokens per second R, generating-only cost is:

kWh / million tokens = (W / R) × (1e6 / 3.6e6) = (W / R) × (5/18)
$ / million tokens = that × your $/kWh

Until W is a measurement, do not substitute 450 or 145 and call the result a local price. You may use 450 W or 145 W as a cap to ask "even at the nameplate, is generating energy in the same decade as this API row?" That is a sanity check. It is not a quote. Add occupancy from the idle envelopes above before you declare victory at low volume.

  • High volume, sunk hardware, long generations. Decode dominates (Fernandez et al., mechanism). Occupancy is amortized. Local energy is the cheap column against most public list prices at household tariffs — once you have a measured W/R, or at least a nameplate sanity check that stays far below the API row.
  • Low volume, always-on resident model. 0.144 kWh/day (Studio idle envelope) or 0.456 kWh/day (4090 desktop-idle envelope) plus the rest of the machine can exceed a cheap hosted mini model even when generating would have looked flattering. Unload or sleep.
  • Prefill-heavy days (long prompts, short answers). Time sits nearer the compute-bound spike. The memory-roof story understates watts and overstates the relevance of bandwidth. Do not budget those days as if they were overnight decode.
  • You do not yet own the card. This page is not a buyer's TCO. See the server guide and workstation builder. Energy after the box is assembled is a different question from whether to buy the box.

Privacy, offline operation, and license control remain reasons to run locally when the energy ratio goes the other way. They are not energy arguments. Keep them in their own column.

What moves the bill besides the nameplate

Four knobs change resident bytes, utilization, or occupancy. None of them require a new invented constant.

  • Quantization. Q8_0 is 1.0 byte per parameter on this site's compression table; Q4_K_M is 0.6. A lighter file lowers the byte term on the memory roof. Throughput can rise. Average watts may fall because the memory system is the thing working. They may not. Measure if you need the ratio.
  • Model size and KV length. A 32B file is 4.6 times a 7B file at the same quant. A long window adds KV that the VRAM guide already treats as first-class. Both raise resident bytes. The catalog is how you pick the smaller model that still does the job.
  • Batching. Several sequences sharing one weight-file trip raise operational intensity and can lift utilization off the floor Fernandez et al. describe for decode. Desk chat is usually batch one. Overnight evals do not have to be.
  • Occupancy. Sleep, unload, or schedule. The idle envelopes are the whole knob. A machine that is not powered has an idle of zero, which no TGP row will tell you.

Mixture-of-experts models change the compute you execute per token but not the weights you must keep resident. Fernandez et al. found their OLMoE variant used more energy than a dense model with a similar active-parameter count, on their A6000-class setup, because the expert kernels were slower than the dense GEMM. That is a mechanism warning, not a 4090 constant. Do not take an MoE's active-parameter count as its decode traffic without reading the runtime's gather.

What this page will not claim

  • No joules-per-token number for a 4090, a 5090, a 3060, or a Mac Studio running llama.cpp. The formula is here. The measured average watts are not.
  • No wall-meter reading invented to finish that formula. 450 W and 145 W are nameplates. 19 W and 6 W are published idle tests. 315 W is a gaming average.
  • No transfer of Fernandez et al.'s A6000/A100 joules onto a GeForce card.
  • No dollars-per-million-token API table copied from a page that was not treated as a static primary source.
  • No carbon factor, no grid mix, no sermon that "AI uses a lot of electricity" without local watts, seconds, and tokens.

Frequently asked questions

So what is joules per token on a 4090?

Unknown here. It is average decode watts on that card in your runtime, divided by decode tokens per second in the same run. This page will not substitute 450 W for the average and will not pretend the bandwidth roof is a measured tok/s. If someone quotes a single 4090 joule figure without a watt trace and a token counter from the same session, treat it as a blog constant, not a spec.

Is local inference cheaper than an API?

On energy, sometimes, and the fork is daily volume versus idle plus whether the day is decode-heavy. After the hardware is sunk, generating energy at household tariffs is often a small column against a public list price — once you have a measured ratio or a nameplate sanity check. Occupancy at the published idle envelopes is tens of watt-hours per day before the rest of the machine. High-volume long generations win. Low-volume resident use loses. Open the API page you actually pay against. This page will not invent that row.

Why not just use the card's TFLOPS rating?

Because batch-one decode does not hit it. Prefill can. Fernandez et al. say prefill is typically compute-bound and decode is typically memory-bound and under-utilized. TFLOPS describe the flat roof. Tokens per second on decode describe the slanted one, which is bytes moved per second divided by bytes per token.

Does a quieter card use fewer joules per token?

Not automatically. If it draws fewer watts and delivers proportionally fewer tokens per second, the ratio is unchanged. If it draws fewer watts because decode never approached TGP, the real ratio is better than a nameplate sanity check. That is the usual desk-GPU situation and the reason 450 W is labeled a cap. Acoustics are not a unit of energy.

Should I leave the model loaded?

For latency, yes, if the next prompt is coming now. For energy, only if the day's token count will amortize the idle envelope. Unloading a 32B so a 4090 can return toward the published 19 W desktop idle is the correct move for a machine that chats twice a day. An overnight batch that will emit for hours should load once and stay there. The getting-started path will get you to a running model. This page is the argument for noticing whether you shut it off afterward.

Where does this sit next to VRAM and stacks?

VRAM decides whether the file plus the window fit. Stacks decide which box you assemble. Joules per token — once measured — decide whether that box, once assembled, should run tonight or yield to a hosted call. Fit first (VRAM guide, recommended stacks), then energy, then taste.

The Gate and the Ledger

Updated: August 20, 2026

You already own the box. The scarce resources are bandwidth, tenancy, and permission — not whether the GGUF file fits.

Ad-free plate · operator thesis
Plate I
Bandwidth

128 GB of LPDDR5x unified memory at 273 GB/s is a wide pool on a narrow corridor. Capacity answers “will it load.” Bandwidth answers “will it move.”

Plate II
Tenancy

One coherent pool, one ledger. A leftover process still owns the corridor after you closed the window. Idle-looking tools are not a vacancy sign.

Plate III
Permission

The operating system is a gate plus a ledger, not a collection of open ports. Membership on a LAN or overlay is routing. It is not identity.

Where the Metaphor Bends

A corridor is not a clock. 273 GB/s is an official peak from NVIDIA’s hardware overview, not a token-per-second promise and not a desk measurement of your workload. A ledger is not a dashboard dump: this page never prints hostnames, bind strings, or session paths. A gate is not “turn the Wi-Fi off.” First-boot hotspot teardown, client isolation, and mDNS failure are network-shape problems that NVIDIA already documented. They are not proof the brick is broken.

The 200-billion-parameter single-Spark figure and the 405-billion dual-Spark figure are vendor claims in NVIDIA’s own user guide. They are not occupancy notes from this desk, and they are not a topology diagram. Treat them the way you treat any marketing ceiling: a published upper bound, not an operating plan.

This is not a buying guide and not a lecture on what unified memory is. If you are still deciding between a VRAM-sized consumer card and a compact Grace Blackwell box, stop here and size the card first. The rest of this page assumes the Spark is already on the desk, the brick is in the wall, and the question has shifted from “does it fit” to “who is allowed to spend the corridor, and who is writing the ledger.”

Why “does the GGUF fit” is the wrong first question

On a discrete GPU you inherit a useful lie: VRAM is a private lake with a posted depth. The site’s VRAM guide is written for that lake. You multiply parameters by bits, add KV cache, add runtime overhead, and you get a cliff. Either the model is resident or the runtime starts walking layers through system RAM and the session dies as a usability failure rather than a clean error.

A DGX Spark does not give you that lake. Official NVIDIA hardware documentation describes 128 GB of LPDDR5x unified system memory, a 256-bit interface, and 273 GB/s of bandwidth on the GB10 Grace Blackwell Superchip. The CPU is a 20-core Arm part (10 Cortex-X925 + 10 Cortex-A725). The GPU is Blackwell with 5th-generation Tensor Cores, 4th-generation RT Cores, and 6,144 CUDA cores. The included brick is 240 W. The SoC’s own thermal design power is 140 W, with the remaining budget reserved for the rest of the chassis — networking, storage, radios, and ports.

That 128 GB number is why people buy the box. It is also why they mis-operate it. A 70B-class GGUF that would never sit in a 24 GB card will load. Loading is not the scarce resource. The scarce resources are:

  • Bandwidth. Every token, every expert swap, every context extension, every leftover tenant walks the same 273 GB/s corridor. Capacity can look generous while the corridor is already full.
  • Tenancy. CPU, GPU, page cache, and any process that allocated from the unified pool are not in separate rooms. They are lines on one ledger. A process you forgot is still a tenant.
  • Permission. The box is a capability. An always-on worker with an unauthenticated listener is not “local AI.” It is an open gate with a confident model sitting behind it.

If you came here for a tok/s table, you will not find one. Invented throughput is how this class of page becomes fiction. If you came here for a dual-Spark wiring diagram, you will not find that either. NVIDIA’s user guide states a vendor claim that two units can host larger models (the 405B figure). That is a published claim, not a floor-plan, and this page does not reconstruct anyone’s private interconnect.

Capacity is not throughput: the 4090 contrast

A GeForce RTX 4090, on NVIDIA’s Ada architecture materials, posts 1008 GB/s of GDDR6X bandwidth into 24 GB of dedicated memory. The Spark posts 273 GB/s into 128 GB of unified memory. That is not a dunk on either product. It is the sentence that should sit on a sticky note above the desk:

Capacity ≠ throughput. The 4090 is a narrow lake with a firehose. The Spark is a wide lake with a garden hose. A 70B that “fits” on Spark and “does not fit” on a 4090 can still be the slower resident, because the weights have to walk 273 GB/s instead of 1008 GB/s.

The quantization guide still applies. Q4_K_M remains the community default because it cuts bytes on the corridor, not because it is fashionable. A smaller model at a higher quant can be the faster, cleaner resident on a bandwidth-bound box for the same reason it wins on a 24 GB card: you are buying quality per byte moved. What changes on Spark is the failure mode. On a 4090, overflow looks like offload and a collapse in tokens per second. On Spark, overflow looks like a shared-pool argument: page cache, SWAP reclaim, a leftover tenant, a runtime that trusted cudaMemGetInfo, or a process that is still allocated after you thought the session ended.

Do not convert 273 versus 1008 into a homemade tok/s table. Bandwidth ratios are not runtime ratios. Context length, batching, quantization, expert routing, and whether the CPU is also dirtying the pool all sit between the two numbers. This page will not invent the interpolation.

The instruments lie, and they lie in opposite directions

NVIDIA’s known-issues page is the operator manual for this section. Two official facts, read together, explain most “the box is haunted” evenings.

nvidia-smi can look idle while a tenant is present

On iGPU platforms, nvidia-smi reports Memory-Usage: Not Supported even though per-process GPU memory is still listed. NVIDIA calls this expected: there is no dedicated framebuffer. If you trained your eyes on discrete cards, you will read that field as “empty” or “the tool is broken” and walk away. The honest read is narrower. The aggregate Memory-Usage column is not a Spark instrument. The process list is. A leftover runtime, a container that did not die, a notebook kernel that still holds a context — those are tenants. They own the pool whether or not the headline field draws a bar.

That is the first teachable shape: nvidia-smi lied idle. The lie is yours if you treated “Not Supported” as vacancy. Official guidance on discrete-card muscle memory does not transfer. System-level memory tools and the per-process column are the ledger. This page will not paste a dashboard or a socket listing. If you need a picture of occupancy, read the process table and the operating system’s own memory counters, then close the leftover tenant.

cudaMemGetInfo can look exhausted while reclaim is possible

The second official fact points the other way. Spark uses unified memory. The CPU can reclaim DRAM by moving pages to SWAP. cudaMemGetInfo does not account for that reclaim. NVIDIA states the reported size may be smaller than what is actually allocatable. A runtime that trusts the API can refuse a load that would have succeeded after reclaim, or it can advertise exhaustion while the operating system still has a path. NVIDIA’s own snippet for a better estimate reads /proc/meminfo for MemAvailable, SwapFree, and huge-page accounting rather than treating the CUDA query as the whole truth. For debugging, they also document a cache-flush workaround and then tell you to restart the application.

That is the second teachable shape: cudaMemGetInfo lied exhausted. The API is not broken. It is answering a discrete-GPU question on a UMA box. If your stack prints “out of memory” at a footprint that should have fit, do not immediately blame the 128 GB sticker. Ask whether the reporter ignored reclaim, whether page cache is sitting on the same ledger, and whether a leftover tenant is already counted against you.

Leftover tenant still owns the pool

Put the two instruments next to a third, ordinary fact: allocation is owned by a process. On a discrete card, killing the server usually returns VRAM in a way you can see. On Spark, the same kill can leave you staring at “Not Supported” plus a pool that still will not admit the next model. NVIDIA’s support note on “memory issues even though I am within capacity” points at cache held in the unified pool and at applications that have not yet learned UMA. The operator translation is simpler than the API discussion: find the leftover tenant and end it. Do not reboot as a personality. Do not flush caches as a ritual before you know who is allocated. Do not start a second server “just to see” while the first one still holds the corridor.

Tenancy is why this page treats the operating system as a ledger. Someone has to write down who was granted the pool, when, and whether they released it. If you do not keep that ledger, the box will keep it for you in the form of surprise exhaustion.

First boot is an operator lesson, not a unboxing vlog

NVIDIA’s first-boot guide is written for day one and then quietly remains true for every later image write. Four facts from that page belong in the standing rules.

  • The machine starts when the brick is connected. Attach display, keyboard, mouse, and network before you seat the supply. You do not get a polite “press power” interlude. A box that “just came on” is behaving as documented.
  • HDMI versus USB-C is a display-path problem. Official troubleshooting: if USB-C / DisplayPort shows nothing, try HDMI. That is not a dead GPU and not a reason to yank power.
  • The setup hotspot tears down when the Spark joins the LAN. Your client then has to find the machine on the network you just joined. NVIDIA lists the failure shapes when that handoff looks like a brick: client isolation on the access point, you are not on the same network, or mDNS does not traverse the network you are on. The documented recovery is a local display and keyboard, not a hardware RMA and not a hunt through someone else’s overlay map.
  • Do not power-cut an image write. Once the download of the software image begins, NVIDIA’s warning is explicit: do not shut down or reboot; interruption can damage the system. The process can continue after the UI says it is rebooting. Wait. This is the same discipline you owe any later recovery or bulk update.

Notice what that list is not. It is not a connect-to-this-URL recipe. It is not a reprint of the sticker on the Quick Start card. It is not a fleet diagram. The teachable residue is the shape: hotspot-to-LAN blamed on hardware is a documented category error. Isolation and name resolution fail in ways that look like a dead box. Write the shape down. Do not publish the name of the network you were standing on.

The operating system is a gate plus a ledger

Most local-AI writeups treat the host as a collection of ports that should be reachable so the laptop UI can attach. That habit is how a capability becomes an accident. On a Spark the blast radius is larger than on a 8 GB hobby card: the same box can hold a serious model, a serious toolchain, and a serious mistake. The correct picture is smaller and stricter.

A gate decides whether the capability is on. A ledger records who turned it on, what endpoint was healthy, what was approved, and what the model proposed. Without both, you get the default-on lane: the brick is in, the runtime is up, something is listening, and “local” is doing the work of an authentication system it is not.

The seven rules below are the standing policy for a Conductor-class local lane. They are paraphrased on purpose. They are not a copy of any private overlay, ack file, or session log. If a sentence seems to want a hostname, a bind string, or a personal path, it is the wrong sentence.

1. Gated local lane

Spark is a capability you enable, not an always-on worker. The brick may stay seated — NVIDIA is clear the unit powers from the supply — but the inference lane, the agent lane, and any listener that can spend the pool are off until a human opens the gate. “It is on the desk, therefore it is serving” is how leftover tenancy and leftover permission accumulate.

2. Default-off

Ship disabled. A human acknowledgement turns the lane on. The same acknowledgement turns it off at session end. If your install path starts a server in the background because that is how the README is written, you have inverted the default. The ack is not a banner and not a chatty status page. It is a recorded human act on the ledger: on, off, by whom, at what time.

3. Local is not authenticated

LAN membership, overlay membership, and “I can ping it from the other room” are routing facts. They are not identity. First-boot already teaches the difference: after the hotspot tears down, being unable to reach the box can mean isolation or mDNS, not that a stranger is locked out. The inverse is also true. If a client can route to a listener, the listener must still demand a login or a token. Reachability is not a password.

4. No app-auth is a defect

If the application cannot present a real login or token, bind it to localhost and leave it there. Publishing an unauthenticated API because “it is only on the LAN” is the defect, not a temporary convenience. Do not compensate by hiding a URL in a private note. Compensate by not opening the gate. This page will not print a no-auth URL for you to try.

5. Queue off until three things exist

Do not attach a job queue to the Spark until (a) the endpoint is healthy, (b) a human has approved this session, and (c) an append-only ledger is actually appending. A queue without a ledger is how a retry storm becomes tenancy: the leftover worker is not a ghost, it is a job you forgot you submitted. Healthy means the process you think is serving is the process that owns the pool — not a stale one that nvidia-smi declined to summarize.

6. Outputs are proposals

A local model that writes a docker line or an ssh line has proposed an action. It has not been authorized to run one. Auto-running because the model was confident is how a gated lane becomes a confused deputy. Keep the human on the gate. The ledger should record the proposal and the approval as separate events. Confidence is not a signature.

7. Negative know-how accumulates

Keep a dated local log of failure shapes. Not hostnames. Not tokens. Not connect strings. “Hotspot tore down, client isolation, looked like hardware.” “Memory-Usage Not Supported, leftover server still allocated.” “cudaMemGetInfo exhausted, MemAvailable disagreed.” The value is the shape. A log that could be pasted onto the public internet without creating a new attack surface is the right log. A log that is a fleet map is the wrong log.

What to do, and what never to do

Do

  • Treat 273 GB/s as the planning number and 128 GB as the occupancy ceiling, not the other way around.
  • Use the supplied 240 W brick. Budget the 140 W SoC TDP as already spent.
  • Prefer NGC containers NVIDIA names for current CUDA behavior (PyTorch, vLLM, TensorRT-LLM) over a host-level version chase.
  • Read per-process occupancy and OS memory counters. Ignore the unsupported aggregate Memory-Usage field as a vacancy signal.
  • End the tenant before you start the next one. Confirm the pool was released.
  • Bind unauthenticated apps to localhost. Add a real login or token before the listener is reachable.
  • Keep the queue off until health, human ack, and an append-only ledger exist.
  • Record failure shapes with dates. Re-read the log before you blame silicon.
  • Seat peripherals before the brick. Wait out image writes. Try HDMI if USB-C is blank.
  • Label 200B / dual-Spark 405B as vendor claims when you repeat them.

Don’t

  • Do not treat “the GGUF fits” as “the session will be fast.”
  • Do not invent tok/s tables from the 273 versus 1008 ratio.
  • Do not run a lesser brick and then file a performance bug.
  • Do not leave the lane default-on because the box is quiet.
  • Do not equate LAN or overlay membership with authentication.
  • Do not publish or bookmark a no-auth URL as the way in.
  • Do not attach a queue to a listener you have not proven healthy.
  • Do not auto-run docker or ssh because the model sounded sure.
  • Do not power-cut an image write or yank the brick to “reset” first-boot networking.
  • Do not paste socket listings, address tables, or dashboard captures into a shared page.

How to keep a negative-know-how log without leaking the shop

The log is local, dated, and boring. That is a feature. A useful entry has four fields and no fifth:

  • Date. 2026-08-20 is a date. “Tuesday after the standup” is not.
  • Shape. One of the rows above, or a new row written in the same grammar.
  • Instrument that misled you. Unsupported Memory-Usage, cudaMemGetInfo, a UI that said “stopped,” a first-boot modal that told you to rejoin a hotspot that no longer existed.
  • What you did that actually released the pool or restored the gate. Ended the process. Waited out the image write. Seated HDMI. Turned the lane ack off.

The fifth field you will be tempted to add is the one this page refuses: the name of the machine, the overlay, the bind, the token, the path of the ack file, the private runbook. Those details do not make the shape more teachable. They only make the log unsafe to store in the same place you store notes about models. If you cannot read the entry aloud on a conference talk stage, it is not negative know-how. It is an inventory of your network.

This is also why the page will not tell you to paste ss, address tables, or a management UI. Those dumps are how operator guides accidentally become overlay maps. The official first-boot and known-issues pages already name the classes of failure. Your log should name the class again, with a date, in your own words.

A session that respects the corridor

Here is a session shape that does not require a private topology to follow. It is a discipline, not a script.

Before the lane comes up. Confirm the 240 W brick is the one NVIDIA shipped. Confirm you are not mid-image-write from a previous recovery. Confirm the last session’s ack is off. Confirm no leftover tenant is allocated. If you cannot confirm tenancy from process occupancy and OS counters, you are not ready to open the gate. Do not “just start it” to see.

Opening the gate. Human ack on. Bring up one runtime, preferably in the NGC container family NVIDIA cites when you need current CUDA behavior. Bind according to whether real app-auth exists. If it does not, localhost only. Do not attach a queue. Do not start a second framework “for comparison” on the same pool. Recommended stacks on this site are for choosing a workload shape, not for running every stack at once on one 273 GB/s corridor.

During the session. Treat every model output that looks like a shell as a proposal. If you are using an agent framework from the CLAWS catalog, the framework is still a tenant and still a proposer. Health of the endpoint is a precondition for any queue, not a trophy you award after jobs are already in flight. If generation is slow, do not reach for a homemade benchmark table. Ask whether the resident weights plus context are walking 273 GB/s, whether another tenant is sharing the hose, and whether you chose a quant that wastes bytes. Quantization is still the lever.

Closing the gate. Stop the runtime. Confirm the tenant is gone. Ack off. Write a negative-know-how line if anything lied to you. The brick can stay connected — first-boot taught you the box powers from the supply — but the lane does not get to stay on because the fans are quiet.

That is the whole operating system picture: a gate you can point to, and a ledger you can read, on a pool whose width and whose corridor are published by NVIDIA and should not be confused with each other.

Frequently asked questions

I already own a DGX Spark. What is the first operating decision?

Decide that the scarce resources are bandwidth, tenancy, and permission. Then put the lane default-off. Everything else — which GGUF, which container, which UI — is downstream of a gate that a human opens and a ledger that records the opening. If your first decision is still “which 70B will load,” you are answering a 4090 question on a 273 GB/s box.

Why is 128 GB not enough to stop thinking about VRAM?

Because 128 GB is shared and 273 GB/s is the hose. Weights, KV cache, page cache, the Arm cores, and any leftover process spend the same DRAM. VRAM arithmetic still tells you how many bytes a model wants. It does not tell you whether those bytes can move in time, or whether someone else already reserved them. Unified memory removed the cliff of “does not fit.” It did not remove the corridor.

Can I run the vendor’s 200B claim on one Spark?

NVIDIA’s user guide states support for models up to 200 billion parameters on one unit, and 405B for a dual-Spark configuration. Those are vendor claims, not measurements from this site, and not a promise about quantization, context, or tokens per second. If you try a model in that class, treat fit as an experiment against the official occupancy of the pool, keep the lane gated, and do not publish a homemade bake-off as if it were a spec.

Why does nvidia-smi say Memory-Usage is not supported?

Because Spark is an iGPU / UMA platform and nvidia-smi’s aggregate Memory-Usage field is built for dedicated framebuffer memory. NVIDIA documents this as expected. Per-process GPU memory can still appear. Use that column and the operating system’s memory counters. Do not conclude the box is idle from the unsupported field.

Why did CUDA say I was out of memory when free memory disagreed?

cudaMemGetInfo can under-report allocatable memory because it does not count pages the CPU could reclaim via SWAP. NVIDIA’s known-issues page is explicit. Their suggested estimate reads MemAvailable and SwapFree (and huge pages) from the kernel. A leftover tenant or a fat page cache can still make the honest number smaller than the sticker. The API lie and the leftover-tenant fact can both be true in the same hour.

The setup hotspot vanished and the machine looks dead. Is the hardware failing?

Usually no. First-boot documentation says the hotspot tears down when the Spark joins the LAN. If you cannot find it afterward, NVIDIA’s own list is client isolation, you are not on the same network, or mDNS does not work on that network. Connect a display and keyboard. Do not power-cut. Do not treat a name-resolution failure as a brick failure.

USB-C has no picture. Should I RMA?

Try HDMI first. NVIDIA’s first-boot notes say some displays have trouble over USB-C / DisplayPort out of the box. Also remember the unit powers as soon as the brick is seated: if you connected the panel after power, you may be looking at a session that already moved on. Seat peripherals first. Do not yank the supply to “refresh” the link during an image write.

Can I use a different power supply to run quieter?

NVIDIA’s known-issues page leads with the supplied adapter. A different or lower-rated supply may reduce performance, prevent boot, or shut the system down unexpectedly. The GB10 TDP is 140 W; the included brick is 240 W because the rest of the system is not free. Quiet is not a license to starve the corridor.

Should the runtime start when the box boots?

No. Default-off. A human ack turns the lane on and turns it off at session end. An always-on worker on a 128 GB pool is how leftover tenancy and missing auth become normal. The operating system can stay up. The capability should not.

Is binding to localhost enough?

It is enough only as a holding pattern while app-auth does not exist. It is not a substitute for a login or a token, and it is not a reason to advertise a URL. If a future change rebinds the same app to a reachable interface without adding auth, you have reintroduced the defect. Localhost is the parking brake, not the lock.

When does a job queue belong on this box?

After three conditions, not before: the endpoint you think is healthy is the tenant that actually owns the pool; a human approved this session; and an append-only ledger is recording submissions and outcomes. A queue without those three is a leftover-tenant factory.

The model wrote a docker command. Can I just run it?

Not automatically. Outputs are proposals. Running container or remote-shell commands because the model was confident skips the gate. Put the proposal on the ledger. Approve it as a separate act, or do not run it. This is especially true on a box that can hold a serious model and a serious toolchain at the same time.

What belongs in NGC containers versus on the host?

NVIDIA’s known-issues page says the CUDA version on the device is verified with the hardware at the software-update release, and that the latest features and performance improvements are available through NGC containers — they name PyTorch, vLLM, and TensorRT-LLM. Prefer that path when you need current framework behavior. Do not treat a host-level toolkit bump as equivalent, and do not collect random containers that were never built for this UMA story. The leftover-tenant problem gets worse when you cannot name which runtime is allocated.

Will this site publish a dual-Spark recipe?

Not here. The 405B figure is a vendor claim in NVIDIA’s guide. A public dual-unit recipe would either invent a topology or leak a real one. Neither belongs on this page. If you operate more than one unit, keep the same three scarcities — bandwidth, tenancy, permission — on each ledger, and keep the interconnect out of published copy.

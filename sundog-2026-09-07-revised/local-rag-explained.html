Local retrieval

Find the Right Passage Before Changing the Model

Follow a wrong answer back to its source, then separate the local costs of embedding models and retrieved context.

By Sundog

7 September 2026

A first retrieval project

You ask your local assistant when the neighborhood workshop closes on Friday. It says six. The current notice says eight. Before downloading another model, I would open the passages the assistant was given. A better answer starts with finding out which notice reached it.

That workshop is an invented example, but it gives us a useful way into retrieval-augmented generation, or RAG. In a simple document question-answering system, software searches a collection, selects passages, and supplies them with your question to the model that writes the answer. Retrieval brings evidence into the request. The original RAG research combined a language model with a retriever and an external document index. [1]

You do not need an embedding formula to start this investigation. You need access to the passages your application actually supplied. If its interface only shows an answer, look for a source or retrieval view. A filename citation can help you find the document; the exact supplied span tells you what the model had available.

A wrong answer can begin with the wrong document

Here is the entire collection for our example. The dates and status labels are invented metadata, and no model run is being reported.

Ask: “When does the workshop close this Friday under the current schedule?” If retrieval supplies only the 2025 notice, it has missed the required evidence. Test a filter using the current/superseded status. If the current notice reaches the model and the answer still says six, inspect the rest of the prompt and how the answer used the supplied material. A different retriever has not yet earned its download.

[OPINION] I like a failure small enough to investigate. “RAG gave a wrong answer” is a complaint. A question, its needed source span, the spans actually retrieved and the answer are a working record.

These are diagnostic experiments, not guaranteed cures. For a first trial I would choose ten questions, mark the answer-bearing spans beforehand, and keep a few additional questions untouched until choosing a setup. Include an exact identifier, a paraphrase, conflicting versions and a question the collection cannot answer. Ten keeps the first trial manageable. A validated acceptance threshold would require further evidence.

Retrieval makes two different demands on local memory

An embedding model represents text as vectors that a search system can compare. The document vectors can be prepared when building the index; a live question needs its own compatible representation. Use the same embedding model for both, unless you deliberately rebuild or otherwise manage compatibility. Ollama's embedding documentation shows this indexing and query distinction. Lexical retrieval searches words or identifiers and need not use an embedding model at all. [2]

An embedding model kept on the GPU occupies memory there. The retrieved passages also add tokens to the answering model's context, which can increase its attention-cache requirement. Moving the embedder to the CPU changes the first cost. Returning fewer or shorter passages changes the second. One choice does not dictate the other. [3] [4]

Keep one generator fixed to see the distinction: Qwen3-14B, using its official Q4_K_M artifact of 9,001,752,960 bytes, or 8.3835 GiB. Its 40 layers, 8 KV heads and head dimension of 128 give an ordinary FP16 attention payload of 160 KiB per cached token. One GiB is 1,073,741,824 bytes. These are planning calculations; the cache article works through the mechanism. [5] [6]

Each row adds the same chosen allowance: 1,024 tokens for the system message and question, plus 512 for the answer, with no earlier conversation. The second row therefore needs about 1.39 GiB more growing cache under these assumptions. A large embedder can return three short passages; a small one can return five long ones.

Combine Nomic on the GPU with the short-passage row and the subtotal is 8.3835 + 0.2547 + 0.4102 = 9.0484 GiB. This omits activations, workspaces, padding, other processes and any additional reserved context. Disk bytes can also differ from loaded tensor storage. I have not tested this stack's fit on a 16 GB card. The subtotal tells you what to inspect when you load it.

The collection has a storage budget of its own

The vector index is another allocation. For scale, 50,000 vectors with 768 F32 components use 153,600,000 bytes, about 0.143 GiB, before text, IDs, metadata, graph links and overhead. That deliberately chosen dimension is not Qwen3-Embedding-4B's maximum output dimension. Use the dimension you actually encoded. FAISS's index documentation separates vector storage from index overhead. [3] [9]

Search can stay on the CPU. You can also sequence GPU embedding and generation so that both models do not remain resident together, accepting load-time and host-memory tradeoffs. If you move an index onto the GPU, check the supported index type and include its allocations; ordinary HNSW and FAISS's documented GPU Flat/IVF implementations are different choices. [10]

[OPINION] I would spend on the questions the small setup actually misses. Keep the passage that changes the answer, the information needed to choose the applicable revision, and the trail back to its source. An archive earns trust one recoverable answer at a time.

Try the diagnosis on one answer

Save one question, identify the required source span, inspect the passages supplied and record the answer. Choose one change from the failure table and repeat with the same generator. For a hands-on embedding API example, use Ollama's embedding documentation; for understanding the returned-text cost, continue to conversation memory.

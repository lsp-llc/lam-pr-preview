Build a reliable agent

Your agent knows which file it needs, asks for it, gets an error and asks the same way again. After a few rounds it announces that the file is unavailable. Before replacing the model, I would inspect the first rejected call. There may be a much smaller repair waiting there.

The harness is the surrounding application that supplies instructions and tools, interprets the model's proposed actions, runs permitted operations and feeds results back. The model's weights are one part of that system. Tool formats and chat templates matter too; llama.cpp's function-calling documentation makes the model/template dependency explicit. [1]

Make the failure small enough to see

Consider an invented tool called read_files. It expects paths to be an array of filenames. The following objects illustrate only its arguments; they are not complete requests for any provider's API.

Expected shape:
{"paths": ["notes.txt"]}

Proposed arguments:
{"paths": "notes.txt"}

Useful validation error:
"paths must be an array of strings; received a string."

Possible corrected arguments:
{"paths": ["notes.txt"]}

The filename is the same. The data shape is different: "notes.txt" is one string, while ["notes.txt"] is a one-item array. A precise error gives the next attempt a particular thing to change. “Tool failed” leaves the agent guessing.

A corrected call still has to execute, and the returned contents still have to be used correctly. If the file genuinely does not exist, valid JSON will not create it. Keep those outcomes separate in the trace.

These are places to investigate, not a rule that the model is always innocent. A model can choose badly even with a clear interface. An application can also lose a good result before the model ever sees it.

Change the interface while keeping the comparison fair

[OPINION] I would keep the weights fixed for the first experiment. Let the current model face a precise error and a bounded chance to correct it. If that repairs the task, I have learned something more useful than whether another download can conceal the same defect.

Start with the failing task and a few similar tasks whose answers you can check. Keep the model artifact, runtime, task and allowed tools unchanged. Compare the old feedback with the precise validation message. Use the same retry limit for both. Preserve the initial proposed call, the error returned, the correction, the tool result and the final task outcome.

What the harness research actually changes

Life-Harness reports improved performance in 116 of 126 model–environment settings, across 18 backbones and seven environments. The count describes how many settings improved. It cannot supply a percentage performance gain for your local agent. The useful consequence is to inspect the surrounding system as something that can be changed and evaluated. [2]

The research can also involve resources far beyond the local agent being debugged. Self-Harness describes a locally deployed Qwen3.5-35B-A3B inference backend using four H200 GPUs. HELIX evaluates 65 candidates over 100 fixtures each; its separate training-data construction is a different stage. None supplies a universal memory allowance or proves that a particular small model will beat a larger one in your application. [3] [4]

The harness also influences what stays in the next request: instructions, schemas, prior calls and tool results. That content can consume context. Its memory consequence depends on the model and runner, which is why the cache calculation and the completed-task comparison belong beside this investigation. There is no reason to invent a fixed GPU charge for the word “harness.”

Keep the useful evidence in the next turn

A useful error is short enough to find and specific enough to act on. In the example, the field name and expected type matter. An entire stack trace may hide them. On the other hand, trimming a successful tool result until its answer-bearing line disappears defeats the purpose of running the tool.

I would keep the smallest result that still supports the next action, then test that choice on the task. If an interface repair becomes a saved skill, give its assumptions the same reuse review as any other instruction.

Inspect one repeated failure

Find the earliest failed transition, save its inputs and returned message, and change one part of that transition. For llama.cpp integrations, start with its function-calling documentation to check model and template support. Keep the old trace. You will want it when deciding whether the repair improved the job.

Find What's Using Your DGX Spark's Memory

Inspect shared memory, find the service owner and read the model allocation before deciding what to restart.

By SundogRevised 7 September 2026

For DGX Spark operators

A model fails to load on your Spark. The aggregate GPU memory field says “Not Supported.” Starting another server is tempting, but I would first find out what is already running. Shared machinery stays useful when its occupants can account for what they left behind.

This is for a DGX Spark operator with terminal access to the host. NVIDIA specifies 128 GB of coherent memory shared by CPU and GPU, at 273 GB/s. The operating system and other processes also use that pool. There is no separate 128 GB allowance for each new model. [1]

The commands below are documented Linux and Docker inspection commands, checked against their references on 7 September 2026. I have not tested this walkthrough on a DGX Spark. Output examples are schematic; use your actual process IDs, container names and runner version.

1. Read the unsupported field literally

nvidia-smi
free -h

NVIDIA documents Memory-Usage: Not Supported on this integrated-GPU platform even though per-process GPU memory is listed. The unsupported aggregate is expected; it is neither an empty pool nor evidence of a broken driver. The same known-issues page explains why cudaMemGetInfo may understate allocatable memory when reclaimable unified memory is involved. [2]

free -h presents host memory and swap in readable units. Look at available as well as free; reclaimable memory makes them different. A particular CUDA allocation or model load can still fail despite an apparently sufficient host estimate. [3]

2. Find the process and the listening service

ps -eo pid,user,etime,rss,comm --sort=-rss | head -n 12
ss -ltnp

The process list shows PID, user, elapsed running time, resident-set size and command name, sorted by RSS. RSS is host resident memory, reported in KiB by ps; use it to find processes worth investigating. It cannot inventory all GPU allocations. Shared pages and other accounting differences mean that adding RSS rows does not reconstruct the whole pool. [4]

ss -ltnp lists listening TCP sockets numerically and requests process information. Find the local port your application uses. Another user's process details may be hidden; an absent owner field does not mean no process owns the socket. [5]

Schematic example, not captured output:
LISTEN ... 127.0.0.1:8000 ... users:(("python",pid=1234,fd=9))

Interpretation:
Port 8000 is associated with PID 1234 in this example.
Inspect that PID before assuming it is the model server.

Once you have an observed PID, inspect its identity and start time. In the command below, replace 1234 with that observed value:

ps -p 1234 -o pid,user,lstart,etime,rss,args

Check whether the process matches the service you intended to run. A parent process can launch workers; a port owner can also be a proxy rather than the inference worker. Command arguments and logs may contain private paths or credentials, so retain the diagnostic locally and redact it before sharing. [4]

3. If the service uses Docker, follow the container

docker ps --no-trunc

This lists running containers with names, images and published ports. Match the relevant port and container name. A host-networked container may not show an ordinary published-port mapping, so keep the host socket observation too. The Docker documentation describes the output and filters. [6]

Replace CONTAINER_NAME below with the actual name from that list:

docker inspect --format '{{.State.Pid}} {{.Config.Image}}' CONTAINER_NAME
docker top CONTAINER_NAME
docker logs --tail 80 CONTAINER_NAME

The inspect expression prints the container's host PID and configured image reference. That PID can belong to an entrypoint rather than the model worker; docker top helps connect the container to its running processes. The log command shows the last 80 lines of the container's available output. These commands do not stop it. [7] [8] [9]

An image tag can move. Keep an image ID or digest in the operational record when it is available, alongside the tag, runner version and launch time. A useful comparison needs to distinguish a configuration change from a new container build.

4. Read what the runner actually allocated

Find the runner's startup record. If the last 80 log lines omit startup, use your retained log file or the service's existing log viewer. Look for the exact weight artifact, effective context, cache types, parallel requests and allocation/error messages. Their field names differ by runner. llama.cpp's server documentation describes separate context, cache and fit controls. [10]

5. Change the identified owner, then repeat one load

[OPINION] I would stop an obsolete service through the manager that launched it, after identifying whose work it is. A deliberately persistent server serving another person deserves a different decision. An unexplained restart can turn a memory investigation into an apology.

Record the before state and the specific change. Repeat the failed load once with the same model and intended settings, then compare its allocation and error. If it fails again, the unchanged request and new observations are useful evidence. Starting more copies makes ownership harder to recover.

These observations narrow the investigation. A particular model still needs a fit check, and load errors can have causes beyond memory pressure. Check the runner's actual error and NVIDIA's current known issues. New CUDA/runtime behavior should be tied to a named compatible build, not assumed from the word “latest.” [2]

Save the record that explains the machine

Keep the service/port, owner, process or container, image/build, model artifact, effective context and exact load error together. The cache article explains why weights alone undercount a session. The bandwidth article explains why enough memory does not guarantee the speed you want.

A shared machine does not need mystery tenants. A name, a launch record and a clear handoff make room for the next useful job.

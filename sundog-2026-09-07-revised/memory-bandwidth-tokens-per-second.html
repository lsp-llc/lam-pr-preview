Why a Model Can Fit and Still Feel Slow

Separate memory capacity from response speed, work through a bandwidth calculation and ask for a benchmark that answers your question.

Understand your hardware

The model fits. Your question is short. The answer still arrives slowly enough to make a new GPU look persuasive. I would put a name to that wait before buying anything. More room and faster replies are different purchases.

Memory capacity is how much a device can hold. Memory bandwidth is how quickly data can move through its memory interface, usually specified in gigabytes per second. For a simple, single-sequence dense-model decode, repeatedly reading weights can be a major part of the work. That makes bandwidth a useful starting hypothesis about speed, with assumptions we can inspect. [1] [2]

Prompt processing is often called prefill; generating the response is decode. A short-prompt generation result does not answer how long a large document takes to process. Nor does the time to load a model explain steady generation after it is resident. Ollama's generation API reports separate load, prompt-evaluation and generation timing fields. [3]

Read one calculation with its units attached

Imagine a dense weight artifact of exactly 5.00 GB, using decimal GB. Assume it is read once for every output token at the device's full specified bandwidth. Ignore attention traffic, computation, dequantization and scheduling. This is a deliberately idealized weight-streaming exercise.

Weight-streaming rate = bandwidth ÷ weight bytes read per token

936 GB/s ÷ 5.00 GB/token = 187.2 tokens/s

That is a calculated screening value for the assumptions above. It is not a measured RTX 3090 result.

The units explain the operation: bytes per second divided by bytes per token leaves tokens per second. The omitted work prevents treating this number as a promised speed. Real kernels may use less than peak bandwidth, and attention, transfers and other computation take time. A roofline model relates work and memory traffic; the quantized kernel still needs its own measurement. [2] [1]

The specifications come from NVIDIA's architecture documents. The bandwidth increase is about 8% from 3090 to 4090 and about 78% from 4090 to 5090. Successive generations do not buy the same change in the bandwidth specification. Measuring generation speed requires another comparison. [4] [5] [6]

A fast memory interface cannot hold an oversized model

The named bartowski Llama 3.3 70B Instruct Q4_K_M artifact checked here is 42,520,398,816 bytes. A 32 GB RTX 5090 cannot keep that complete artifact in its local memory, even before cache and runtime allocations. CPU offload changes the configuration and introduces another memory path to measure. [7] [6]

DGX Spark makes the capacity/speed distinction easy to see: NVIDIA specifies 128 GB of unified memory at 273 GB/s. That larger pool admits different candidates from a 32 GB card, while the lower bandwidth specification asks a different question about single-session generation. The operating system and other processes also use the shared pool. [8]

[OPINION] I would screen for the complete session first: weights, context and the rest of the runner. Then I would compare measured speed among configurations that can do the job. The card already paid for gets to compete.

Four cards do not automatically give one token four buses

In a serial layer split, different cards hold different layers, and a token's computation passes through those layer groups in sequence. llama.cpp documents layer split as pipeline parallelism. More cards can supply capacity without multiplying the bandwidth available to that one sequential pass. [9]

Simplified example: four identical RTX 3090s

Each reads one quarter of a 42.5204 GB dense artifact, sequentially.

Total weight-read time = 4 × (42.5204 ÷ 4) ÷ 936 ≈ 0.0454 seconds.

Idealized rate ≈ 22.0 tokens/s, using one card's 936 GB/s for the serial pass.

This model excludes transfers, attention and other work, and is not a four-card benchmark. Tensor parallelism can put several devices to work on the same layer but adds communication. Concurrency can change pipeline use too. Ask which split mode, workload and interconnect produced a result before treating “combined bandwidth” as a speed claim. [9] [10]

Where the weight-streaming picture stops being enough

Mixture of experts. An MoE model activates a subset of experts for a token. Stored size and active work are different quantities, so dividing by the entire file is not the same model of traffic. Qwen3-Coder-Next's card distinguishes total and active parameters. [11]

Speculative decoding. A draft-and-verification scheme changes the relationship between a main-model pass and emitted tokens. Record whether it is enabled when comparing results. [12]

Compute specifications. Peak FP32 throughput divided by bandwidth describes an FP32 reference roofline ridge. It does not establish a quantized kernel's throughput or locate a Q4 decode bottleneck by itself. [2]

Ask for the benchmark that answers your question

Choose a short exchange and a longer task that currently feels slow. Keep the model artifact, runner build, placement and concurrency fixed across hardware where possible, and state any necessary difference. Record load time, prompt-processing time, generation rate and total completed-task time separately. For a setting that fits only after reducing context, write down the context that actually loaded.

Was the answer usable for the task?

In Ollama's final generation response, eval_count counts generated tokens and eval_duration is their evaluation time in nanoseconds. For that reported interval, tokens/s = eval_count / (eval_duration / 1e9). Keep prompt-processing and load time alongside it when the whole wait matters. [3]

I have not run a hardware comparison for this article. The calculations tell you what evidence to request. A repeatable reduction in the wait you actually have is a reason to consider an upgrade. Until then, a larger number on the box is still only a specification.

Measure one short and one long task

Use the same working configuration and save both timing records. If memory is the obstacle, start with the session budget. If you are comparing an always-on machine with one that rests between requests, include the hours between the tokens.

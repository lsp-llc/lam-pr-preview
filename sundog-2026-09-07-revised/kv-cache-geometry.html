Why a Longer Chat Needs More Memory

Understand weights, KV cache and runtime allocations; follow one calculation and check the context your model actually loaded.

Understand your local model

The model downloaded. It answered a short question. Then you gave it a long document and the comfortable setup stopped being comfortable. The file did not get larger. The session asked for more room.

For models that use attention, the KV cache stores keys and values calculated from tokens already processed, so later generation can reuse them. A token is a piece of the model's encoded input or output. A word can span several tokens. The model's weights, this session state and the runner's other allocations all belong in the memory budget. [1]

Context is the token budget available to a request or session, subject to the model and runner. Your question, supplied documents, retained conversation and generated output can compete for it. An advertised maximum is not the same thing as the amount your local configuration can afford. The runner may reserve cache in advance, so memory need not rise one small step at every new message. [1]

Work out one model before comparing two

Use Qwen3-32B and one sequence. Its configuration gives 64 attention layers, 8 key/value heads and a head dimension of 128. Choose FP16 for both keys and values: two bytes per stored value. These architecture inputs are properties of this model; the number of cached tokens and the supported cache precision are configuration choices. [2]

Growing KV bytes

2 × attention layers × KV heads × head dimension × bytes per value × cached tokens

For Qwen3-32B at FP16:
2 × 64 × 8 × 128 × 2 = 262,144 bytes per token = 256 KiB per token.

At 32,768 tokens:
262,144 × 32,768 = 8,589,934,592 bytes = 8.00 GiB.

The leading factor of two counts keys and values. One KiB is 1,024 bytes; one GiB is 1,073,741,824 bytes. The formula describes the growing payload of an ordinary attention cache with those inputs. It does not include every allocation made during a run.

Now add the exact official Q4_K_M weight file: 19,762,149,024 bytes, or 18.40 GiB. The file-plus-KV subtotal is 26.40 GiB. A 24 GiB device cannot keep that entire subtotal locally at this setting, even before other allocations. Reducing the session budget, using another supported cache precision, offloading, or choosing a different model are separate experiments. [3]

Notice the two precision choices. Q4_K_M describes the weight artifact. FP16 describes the cache in this calculation. Downloading quantized weights does not automatically mean the cache uses the same precision. llama.cpp documents independent key and value cache controls. [1]

Two similar files can leave very different room to talk

Granite 4.0 h-small's Q4_K_M file is 19,476,621,984 bytes, or 18.14 GiB. It has four attention layers with the same KV-head count and head dimension used above, plus 36 Mamba layers. Its growing attention payload is 16 KiB per token. The Mamba layers need recurrent state of their own; omitting that state from the growing KV term does not make it free. [4] [5]

I have not tested either model's maximum usable context on a 24 GiB device. Granite's last row makes a long-session configuration worth investigating; it does not establish a successful load, answer quality or generation speed.

[OPINION] I would read the attention layout before spending an afternoon downloading a model for a long conversation. A small difference between files can hide a large difference between sessions. The useful comparison includes the work you meant to finish.

Check what your runner actually loaded

For an already running local model in Ollama, open a second terminal and run:

ollama ps

Read NAME, CONTEXT and PROCESSOR. The context column reports the allocated context; processor placement distinguishes GPU, CPU or a split. Compare that with the context you requested. The command reports the loaded configuration. Check the answers separately to see whether the model uses a long conversation correctly. Ollama's context page shows the current output layout and the app setting. [6]

An interpretation sheet, not captured output
ObservationMeaning for the next check
Allocated context is smaller than intendedInspect the setting used for this request and the runner's load record.
Processor placement includes CPUYour run uses a different memory path from an all-GPU comparison.
The context matches, but a needed early fact is missedInspect truncation and retained prompt content, then answer quality.

For llama.cpp, use its own server documentation and startup log instead. Record the build, effective context per sequence, parallel slots and key/value cache types. Its fitting option adjusts unset parameters. An explicit requested value and the allocation the runner ultimately made are different observations. [1]

Then try one task near your intended working length, leaving room for the answer. Put a fact you can check near the beginning and inspect what the application actually sends. A correct answer supports a conclusion about that one request. Dependable recall across the whole window needs broader evaluation.

Go deeper: sliding windows and cache quantization

Some layers stop growing before others

OLMo 3.1 32B has 16 full-attention layers and 48 sliding layers with a 4,096-token window. At 65,536 tokens, a simplified cache honoring those windows has the storage of 19 full-length layers: 16 + 48 × 4,096 / 65,536. Treating all 64 layers as full attention overstates this term by about 3.37 times. The fourfold ratio describes long-context growth, not the total at this length. [7]

The implementation matters. llama.cpp exposes --swa-full, which changes sliding-window allocation. The pinned implementation checked here is revision 465e49b9cea7; inspect the behavior of your installed build. [8] [9]

Cache precision buys a different experiment

In the pinned llama.cpp block layout, 32 FP16 values occupy 64 bytes, q8_0 occupies 34 and q4_0 occupies 18. Their payload ratios are 53.125% and 28.125% of FP16 before padding and other buffers. Applied to the Qwen example, q4_0 takes its 8.00 GiB attention payload to 2.25 GiB and its file-plus-KV subtotal to 20.65 GiB. [10]

That storage saving does not establish quality or speed. Memoriant's corrected GB10 results used Nemotron-3-Nano-30B-A3B-UD-Q4_K_XL.gguf and llama.cpp build 8399. Reported FP16 versus q4_0 generation was 44.6 versus 39.3 tokens/s at 24K context and 38.0 versus 24.0 at 110K, with essentially equal short-context speed. I have not reproduced the benchmark. Keep its model, build and workload with the numbers. [11]

Keep the exact artifact, context, cache types, parallelism and observed result together. Another evening's conversation may be longer. A useful memory budget tells you which part of the setup to revisit when it is.

Hardware tradeoffs

Why a Model Can Fit and Still Feel Slow

To write each new word, your hardware reads the model's weights from memory again. Once you see that, token speed becomes arithmetic you can check.

By Sundog

Rewritten 24 September 2026

For anyone choosing hardware or a model size · One formula, checked against 32 published benchmark results

Load a model that fits comfortably in memory, ask it a question, and watch it type. How fast it types was mostly decided before you pressed Enter, by one number on your hardware's spec sheet and one on the model file.

The two numbers are memory bandwidth, how many gigabytes per second the processor can read from memory, and the size of the weights the model must read to produce each word. Once you see why those two dominate, you can avoid an expensive mistake: buying memory capacity when you needed memory speed, or the reverse.

To write each word, the model rereads itself

A language model writes one token at a time, where a token is a word or a piece of one. To produce each token, the whole network runs once from input to output. In a typical model, every weight takes part in that pass: it is fetched from memory, used in a multiply and an add, and set aside until the next token, when it is fetched again.

For one person chatting, that means each weight crosses from memory to processor to do about two arithmetic operations. Modern processors can do arithmetic far faster than memory can deliver numbers, so most of each token is spent waiting for weights to arrive. Generation speed becomes a question of how fast the weights can be streamed, which gives a useful ceiling:

tokens per second ≤ memory bandwidth ÷ bytes read per token

In an ordinary dense model, where every weight is used for every token, the bytes read per token are roughly the size of the weight file. Mixture-of-experts models, described below, break that rule in a useful way.

Real speeds land below these ceilings, because no program uses every byte of bandwidth and each token needs some other work. The ceiling is still the most useful single number you can compute before buying anything. [1] [2]

Does the ceiling hold? Thirty-two published results say yes

The llama.cpp community keeps two public benchmark threads that make an unusually clean test. Both run the same model, Llama 2 7B compressed to 4 bits (a 3.56 GiB, or 3.82 GB, file), with the same benchmark tool. One covers Apple Silicon chips from the M1 to the M4 Max, all measured on one software build from November 2023. The other covers NVIDIA hardware, measured on 2025 builds. [3] [4]

Across all 32 results, speed and bandwidth correlate at 0.95. Every point sits under the ceiling, as it must. The slow chips get close to it: an M1 with 68 GB/s reaches 80 percent of its ceiling, and the DGX Spark reaches 80 percent of its own at 57 tokens per second. Among the Apple chips, the fastest fall furthest below the line: the Ultras, listed at 800 GB/s, reach only 36 to 45 percent.

The same Apple thread also timed an 8-bit file of the same model, and that shows what is happening. On a slow chip, cutting the file from 8 bits to 4 almost doubles the speed: the M1 went from 7.92 to 14.19 tokens per second, 1.79 times faster, close to the 1.87 times that the smaller file allows. On the 76-core M2 Ultra, the same change gave only 1.41 times. On fast chips, other per-token work, probably including unpacking the compressed weights, takes a real share of the time. Software matters too: the thread's later entries show newer llama.cpp builds lifting that M2 Ultra from 94 to 125 tokens per second, from 45 to 60 percent of its ceiling, on the same hardware. [3] The ceiling is the right first estimate everywhere. On the fastest hardware, expect a wider gap.

Why reading your prompt is so much faster

If you have watched a local runner's timing output, you may have noticed that it reads a long prompt at hundreds or thousands of tokens per second, then writes its answer at a few dozen. The same benchmark threads show it plainly: an RTX 3090 processes a 512-token prompt at about 5,175 tokens per second and generates at about 158, a 33-fold difference on the same model and hardware. The DGX Spark reads at about 3,062 and writes at about 57. [4]

When the model reads your prompt, all of its tokens are already known, so the runtime can push many of them through each layer at once. Each weight fetched from memory now does arithmetic for hundreds of tokens instead of one. The work stops waiting on memory and starts waiting on arithmetic. Engineers call the two phases prefill and decode, and research on serving systems treats them as different workloads for exactly this reason: prefill is limited by compute, and decode, at the one-request-at-a-time batch sizes typical at home, by memory bandwidth. [5] [6]

The roofline model, from Williams, Waterman and Patterson, captures this with one ratio: operations performed per byte moved from memory, which they call operational intensity and many engineers call arithmetic intensity. [7] A chip has a ridge point, its peak operations per second divided by its bandwidth; work below that ratio is limited by memory. The RTX 3090's tensor cores can do 71 to 142 trillion 16-bit operations per second, depending on how they accumulate results, which against 936 GB/s puts its ridge point at roughly 76 to 152 operations per byte. [1] Generation does about two operations for each weight it reads: about 1 operation per byte with 16-bit weights, and about 4 with 4-bit weights. Even against the lower ridge point, at most about 5 percent of the chip's arithmetic capacity is in use during single-user generation.

Three ways past the bandwidth limit

That gap leaves two kinds of fix: read fewer bytes for each token, or get more tokens from each read. The second finally puts the idle arithmetic to work.

1. Read fewer bytes

Quantization stores each weight in fewer bits: an 8-bit file is about half the size of a 16-bit one, and a 4-bit file about a quarter. Fewer bytes per token raises the ceiling. As the M2 Ultra showed, it does not guarantee a matching speedup, and speed is not the only thing that changes.

Shi and Ding measured eleven quantization methods on Llama-2 and CodeLlama models served with TensorRT-LLM, NVIDIA's own serving engine, on H100 GPUs, tracking latency, energy and quality together. No method won on all three. One 4-bit-weight configuration had the best tail latency, meaning the speed of the slowest responses, at moderate load, while some other quantized setups did not reduce latency at all, and compressing the KV cache (the model's stored notes on the conversation) sometimes erased the gains. Quality moved too: one 8-bit integer setup that also compressed the model's intermediate values cut a 13B model's coding pass rate by up to 92 percent. [8] Those results belong to that engine and those GPUs, not to a GGUF file, the format llama.cpp and Ollama use, on your machine. They are a good reason to measure speed and quality together.

2. Read only part of the model

A mixture-of-experts (MoE) model splits many of its layers into specialist blocks and routes each token through only a few of them. Every expert must sit in memory, but only the chosen ones are read for a given token. OpenAI's gpt-oss-120b has about 117 billion parameters and activates about 5.1 billion per token. Qwen3-30B-A3B has 30.5 billion and activates 3.3 billion, 8 of its 128 experts at a time. [9] For the bandwidth ceiling, gpt-oss-120b behaves more like a 5-billion-parameter model than a 117-billion one, while still needing memory for all 117 billion.

That is why MoE models suit machines with a lot of memory and moderate bandwidth, such as a DGX Spark or a high-memory Mac: the memory holds every expert, and the bandwidth only has to carry the few in use.

3. Get more tokens from each read

If each pass over the weights produced several tokens instead of one, the idle arithmetic would finally have a job. Two techniques do exactly that.

Batching serves several requests at once, so one pass over the weights advances all of them. It is how servers get their throughput, and it helps at home when several agents or users share one model. It raises total output, not the speed of any one chat, and each request needs its own KV cache.

Speculative decoding helps a single user. A small, fast draft model guesses the next few tokens. The large model then checks all the guesses in one pass, which costs about the same memory traffic as generating one token, and keeps the guesses up to the first one it rejects. Leviathan, Kalman and Matias designed the acceptance rule so the output follows exactly the same probability distribution as the large model alone, and reported 2 to 3 times faster generation on T5-XXL. [10] A DeepMind team independently reported 2 to 2.5 times on the 70-billion-parameter Chinchilla. [11] It works best when the draft guesses well, which is common for predictable text such as code. llama.cpp's server can load a draft model alongside the main one; its option names changed during 2026, so follow the current documentation. [12]

Capacity is the other half of the decision

None of this matters if the model does not fit. A 24 GB card with 936 GB/s cannot hold a model whose weights need 40 GB; it can run one only by spilling layers into slower system memory. A DGX Spark with 128 GB of unified memory can load that model, but at 273 GB/s its ceiling for a dense 40 GB file is about 273 ÷ 40 ≈ 7 tokens per second. [2] One machine offers room and the other offers speed. Which one you need depends on the models you actually intend to run, and an MoE model can make the roomy machine the fast one too.

Two more things lower your speed, and the same formula prices both. The KV cache is read on every token as well. With 16K tokens of conversation, Qwen3-32B's cache adds 4 GiB to its 18.4 GiB of 4-bit weights, which lowers an RTX 3090's ceiling from about 47 to about 39 tokens per second. And if part of a model spills from the graphics card into system memory, those layers are read at system-memory speed: with 10 percent of a 20 GB model in 89.6 GB/s memory, the ceiling falls from about 47 to about 24 tokens per second. Both figures are my arithmetic from the formula, not measurements. Why a Longer Chat Needs More Memory shows how to calculate the cache for your own model.

Check your own number against the ceiling

Ollama's API reports the number of generated tokens (eval_count) and the time spent generating them (eval_duration, in nanoseconds), separately from loading and prompt reading. Generation speed is eval_count ÷ eval_duration × 10⁹, and ollama run with --verbose prints these timings, including the generation rate, after each answer. [13] Divide your measured speed by the ceiling from your bandwidth and model file. For scale, in the benchmark results above, chips under 550 GB/s reached 52 to 84 percent of their ceilings, the NVIDIA machines 62 to 80 percent, and the 800 GB/s Ultras 36 to 45 percent.

  • Far under half, on ordinary hardware: something else is in the way. Check whether layers are running on the CPU, whether another program is competing for the GPU, and how long the conversation is.
  • In the ranges above: the hardware is doing roughly what it can. Only fewer bytes per token, an MoE model, speculative decoding or more bandwidth will make generation much faster.

[OPINION] Before buying hardware for local AI, I would write down the models I want to run, check that their weights and a realistic context fit, and then divide bandwidth by weight size. That two-minute calculation beats most spec-sheet comparisons, and it tells you whether to spend on memory size or memory speed.

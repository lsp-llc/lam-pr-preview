Fix the Tool Loop Before You Replace the Model

One published agent failure, traced call by call, shows where schemas, constrained decoding, honest errors and a final check fix problems a bigger model would not.

By Sundog

Rewritten 24 September 2026

For anyone running a tool-calling model or agent · Built around one published failure trace

An agent was asked for a report on the week's five trending movies. Its last action saved a file, and the final line of its log read Successfully wrote to trending_movies_report.md. The file held one sentence: Markdown content with movie details and trailer links. Every tool call before it had failed.

That run is printed in the appendix of LiveMCP-101, a benchmark that gives agents multi-step jobs with real tools, connected through MCP (the Model Context Protocol, a shared standard for plugging tools into models). It is worth reading slowly, because very little of it has to do with how much the model knows about movies. [1]

Read it the way you would read a repair log. The first call asked for page "1", the text, when the tool expected the number 1. The server caught the mistake and said precisely what was wrong. The model's next line of reasoning began "After getting the list of popular movies," and carried on as if the call had worked. Having no real movie IDs, it passed the phrase "ID of the first movie" as an ID. Having no titles, it searched YouTube for "Title of the first movie trailer." The one call that succeeded wrote a placeholder to disk, and the loop allowed "Successfully" to be the last word.

The model made two mistakes: a wrong type, then an ignored error. The program around it made two more, letting the run continue after a required step failed and accepting a placeholder as the result. A bigger model would still be running inside that same program.

The harness is everything between the model and the world

A language model cannot open a file or call an API. It writes text. The harness is the program that runs this tool loop: it tells the model which tools exist, reads the tool call the model writes, checks it, runs it, and decides what the model sees next. Each tool comes with a schema, a machine-readable list of its arguments and their types. Coding agents, chat apps with plugins and MCP clients all contain a harness, whether or not they use the word.

That is why it pays to trace a failure before choosing a remedy. If you only read the agent's closing message, whether it is an apology or a cheerful "done," every failure looks like the model's fault, and the natural response is to download a larger one.

Make the wrong shape impossible to write

The "1" mistake has a cure that is almost unfair, and it is one of the places where running a model locally gives you more control, not less.

At every step, a language model assigns a probability to each token in its vocabulary (a token is a word or a piece of one), and a sampler picks one. Constrained decoding adds a filter before the pick: any token that would break a required format is removed from the candidates. If the schema says page is an integer, then after "page": a quotation mark is no longer available. The model can still choose the wrong number. It cannot choose the wrong type.

Checking every token in a vocabulary that often exceeds 100,000 entries against a grammar, at every step, sounds slow. Willard and Louf, whose 2023 paper describes the method behind the Outlines library, showed how to do most of that work in advance. They convert a regular expression or grammar into a finite-state machine, then precompute an index of which vocabulary tokens are legal from each state. During generation, filtering becomes a lookup instead of a scan. [2]

Local runtimes expose this directly. llama.cpp accepts grammars written in its GBNF format and can convert a JSON Schema into one. Ollama accepts a JSON Schema in the format field of a request. [3] [4] A hosted API decides for you whether this control exists. On your own machine, it is a setting.

One detail catches people out. A schema inside a tool definition is shown to the model, but in llama.cpp a schema passed only as an output constraint (json_schema or response_format) never enters the prompt. Ollama's documentation likewise recommends describing the schema in the prompt as well. [3] [4] A model forced into a format it was never told about will fill it, but not necessarily sensibly.

What a grammar guarantees, and what it cannot

A schema-constrained sampler guarantees that the output parses and that every field has an allowed type and name. It does not guarantee that the values are right. {"page": 1} and {"page": 7} are equally valid, and only one of them may be what the task needed. It also cannot make a model call a tool it has decided not to call.

Constrain the call, not the thinking

There is a catch. Tam and colleagues tested what happens when a model must answer inside a strict format such as JSON. On reasoning tasks, accuracy often fell, and stricter formats generally cost more. The most dramatic case came from instructions alone: Claude 3 Haiku's score on GSM8K, a set of grade-school math word problems, fell from 86.99 to 23.44 when the prompt spelled out a JSON schema instead of simply asking for JSON. Classification tasks, where the answer is a fixed label, sometimes improved. [5]

The paper also found a telling mechanism. In JSON mode, GPT-3.5-Turbo put its "answer" field before its "reason" field in every one of the responses they examined on one task. The format quietly turned "think, then answer" into "answer, then justify." [5] The team behind Outlines disputed the headline result: rerunning the tests with prompts matched between the free and structured versions, they found structured output slightly more accurate. [6]

[OPINION] Read together, the two suggest a practical rule. Let the model reason before it commits: in ordinary text, or in a reasoning field placed before the answer field. Apply the strict constraint to the part a machine will execute, the tool name and its arguments. The model decides what to do in its own words, and the grammar makes sure the request it writes can be parsed.

For one popular local model, half the failures were the fixable kind

LiveMCP-101's error analysis sorts failed runs into seven types, from ignoring a requirement to misreading a tool's output. For most of the ten models analyzed, the most common failure was a semantic error: a well-formed call with the wrong meaning, such as the wrong entity or an over-broad search. The strongest models failed this way on roughly 16 to 25 percent of tasks, and GPT-4.1-mini on about 42 percent. [1]

Syntactic errors, meaning malformed parameters with wrong types, missing fields or invalid structure, were negligible for the frontier models. For Llama-3.3-70B-Instruct they reached 48 percent of tasks. The authors suggest a plausible cause: the Model Context Protocol spread after Llama 3 was released, so the model had little MCP-specific training. Its overall success rate in that benchmark was 1.98 percent. [1]

That split matters if you run models at home. It is not a rule about open models: Qwen3-235B-A22B, also open, made almost no syntactic errors in the same study. But for Llama 3.3 70B, a model many people run locally, nearly half of all tasks failed on exactly the class of error a schema-constrained sampler is designed to rule out. Removing that class would not guarantee success, because the semantic errors behind it would still be waiting. It would move the failure to where the model's own judgment is being tested, which is where a model comparison starts to mean something.

Changing the interface can move results a long way

The clearest early evidence came from coding agents. For SWE-agent, Yang and colleagues designed what they called an agent-computer interface: a small set of commands for viewing, searching and editing files, built for a language model instead of a person. With GPT-4 Turbo, it resolved 12.47 percent of the full SWE-bench, 286 of 2,294 real GitHub issues, when the best previous system managed 3.8 percent. [7]

The ablations are the interesting part, because each one changes only the interface. On a 300-issue subset where the full design scored 18.0 percent:

One interface change at a time (SWE-agent, GPT-4 Turbo, SWE-bench Lite)
Interface changeIssues resolved
Full design: edit command with a syntax check, 100-line file viewer, summarized search18.0%
Edit command without the syntax check15.0%
No edit command, shell tools only10.3%
Viewer shows the whole file12.7%
Viewer shows 30 lines14.3%
Step-by-step search instead of summarized results12.0%
No search tool at all15.7%

Showing the model the entire file made it worse. So did a search tool that returned results one at a time, which did more harm than having no search tool at all. And a syntax check that rejected broken edits before they landed was worth three points on its own. The movie run had a gate like that; what it lacked was a loop that refused to continue until the call was fixed. [7]

LIFE-HARNESS, from Xu, Wen and Li, improves the harness systematically while leaving the model's weights alone. It has four layers: a contract describing each tool and its rules, a store of procedures learned from earlier runs, an action layer that checks each proposed call before it executes (rewriting it into a valid form, or blocking it), and a regulator that watches for repetition, stalls and exhausted budgets. The authors evolved the harness using runs from one small model, Qwen3-4B-Instruct, then froze it and reused it with 17 other open-weight models. [8]

Across seven rule-governed environments, from text-based household chores (ALFWorld) to database tasks (DBBench), the harness improved results in 116 of 126 model and environment pairs. Averaged over all 18 models, ALFWorld success rose from 41.1 to 75.7 percent. Qwen2.5-32B with the harness also beat xLAM-2-32B, the same base model fine-tuned specifically for tool use, by 7.5 points on the in-domain benchmark, and the harness still improved xLAM itself. [8]

Harness-R1, from Shao and colleagues, trains a separate 9B "harness engineer" model to read batches of failed runs and write executable patches for the harness. On three agent benchmarks, the average success of Qwen3.5-9B rose from 44.3 to 53.6 percent with those patches, and on a separate set of 1,270 held-out tasks the patches still added 8.9 points. The comparison I find most instructive is a negative one. Self-Refine, a method in which the model critiques and revises its own work, lowered the same average to 41.8 percent. Here, self-critique cost 2.5 points and harness patches added 9.3. [9]

The paper also measured which moments mattered. Removing the patches that act just before a tool call cost 3.9 points, and removing the ones that act just after tool feedback cost 3.3. Those are the two moments where the movie run went wrong: a malformed call that could have been corrected before execution, and an error that needed to change what happened next. [9]

What these results do not show

LIFE-HARNESS was tested on deterministic environments with stable tools, its authors describe it as work in progress, and 10 of its 126 settings did not improve. Harness-R1's main scores were measured on the batches its patches were written for, and three of 63 unseen target combinations got slightly worse. Neither paper shows that a small model with a good harness beats a large model at your job. They show that the interface is a large, measurable part of the result, which is reason enough to fix it before drawing conclusions about the model.

Four repairs to try before a new download

These follow the order of the loop. Each can be tested with the model held fixed.

1. Make the tool description tell the whole truth

State every argument's type, which ones are required, allowed values, and one correct example call. Give tools names and descriptions that do not overlap, so choosing between search_files and find_file is not a coin toss.

2. Constrain or validate the call before it runs

Where your runtime supports it, constrain tool-call arguments with the tool's JSON Schema. Where it does not, validate the call against the schema before executing it. Some mismatches can be repaired safely: a string "1" for an integer field can become 1. LIFE-HARNESS's action layer does this kind of rewriting, or blocks the call outright. [8]

Check the runtime, too

llama.cpp's documentation notes that tool calling depends on the model and its chat template, that a generic fallback format can use more tokens than a model's native one, and that heavily quantizing the KV cache (for example with -ctk q4_0) can substantially degrade tool calling. [10] If you shrank the cache to fit a longer context, test your tools again.

3. Stop a cascade, and return errors the model can act on

The movie run's error was already exact, so a clearer message is only half the repair. Make failure sticky: if a required step has not succeeded, later steps that depend on it should not run on placeholders. Count identical failed calls and stop after a small limit with an honest report. Where your tools return vaguer errors than that one, say which field failed, what was expected and what arrived. An illustrative reply:

{"ok": false,
 "tool": "tmdb-movies.get_popular_movies",
 "error": "page must be an integer; received the string \"1\"",
 "hint": "call again with {\"page\": 1}"}

4. Check the result, not the claim

Before the harness reports success, verify the artifact. For the movie job, that means the file exists, contains five entries, and each entry has a title, cast and a link. A ten-line check would have turned the fake success into a clear failure.

[OPINION] I would spend an afternoon on these four before spending a download on a bigger model. If the same task still fails with honest schemas, constrained calls, a loop that stops on failure and a result check, the remaining failures are about judgment: wrong values, wrong tools or skipped steps. That is the point where swapping models becomes a fair experiment instead of an expensive guess.

Replay one failure, one repair at a time

Save the full trace of one failed agent run: each proposed call, the validation result, the tool's reply and the model's next step. Label the first step that broke. Apply the matching repair from the list above, change nothing else, and run the same task again alongside two tasks that already worked, so a fix for one job does not quietly break another.

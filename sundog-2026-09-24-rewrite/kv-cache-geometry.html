Memory and context

Why a Longer Chat Needs More Memory

Every token in a conversation leaves notes in every layer of the model. Learn to price those notes, see how model designers shrink them, and set context on purpose.

By Sundog

Rewritten 24 September 2026

For anyone who has run out of memory with a long document or chat · Includes a cost table for ten popular models

A 32-billion-parameter model answers a short question comfortably on a 24 GB graphics card. Raise its context setting so a long contract fits, and it slows to a crawl or fails to load. The model did not get any bigger. The space for its notes on your conversation did.

Those notes are called the KV cache, and they are the second large object living in your GPU's memory, next to the model's weights. The weights have a fixed size you can read off the download page. The cache grows with every token you send and every token the model writes, and at long context it can rival the model itself. Many runtimes reserve room for the whole context setting as soon as the model loads.

Why the model keeps notes at all

A transformer decides what to write next by letting the newest token "look back" at every earlier token, in every layer. Each layer turns each token into three vectors. The newest token's query is compared with every earlier token's key, and the token then draws most from the values whose keys matched best. Each layer runs several of these comparisons side by side, called attention heads. A query is used once and thrown away, but every key and value will be needed again by every later token, so those are the vectors worth keeping.

Without a cache, the model would recompute the keys and values for the entire conversation every time it produced a new token, and the total work would grow with the square of the conversation's length. With a cache, each token's keys and values are computed once and stored. The KV cache is a trade: memory spent to avoid repeating arithmetic.

The cache stores a key and a value for every token the model can still see, in every layer, for every KV head. Multiply by the length of each vector and the bytes per number, and you have its size.

Price one token, then multiply

For a standard decoder model, the cache for a single token is:

bytes per token = 2 × layers × KV heads × head size × bytes per number

The 2 counts the key and the value. Layers is the depth of the network. KV heads is how many separate key and value sets each layer keeps, which is often fewer than the number of attention heads, for reasons explained below. Head size is the length of each vector. Bytes per number is 2 for the usual 16-bit cache. The first three are in the config.json file on the model's Hugging Face page, as num_hidden_layers, num_key_value_heads and head_dim. For a model you run in Ollama, ollama show --verbose prints the model's metadata, including keys ending in block_count, attention.head_count_kv and attention.key_length. [1] [7]

Qwen3-32B has 64 layers, 8 KV heads and a head size of 128. [1] So each token costs:

2 × 64 × 8 × 128 × 2 bytes = 262,144 bytes = 256 KiB per token
256 KiB × 32,768 tokens    = 8 GiB for one 32K-token conversation

Qwen's own 4-bit file for this model, Qwen3-32B-Q4_K_M.gguf, is 18.40 GiB. (A GiB is about 7 percent larger than a GB; a card sold as 24 GB holds 24 GiB.) Add the cache and you can see roughly where a 24 GiB card gives out: somewhere between 16K and 32K tokens, or sooner once the runtime's own working memory is counted.

Every doubling of context doubles the cache. Serve two conversations at once and you need two caches. Change the weights from 4-bit to 8-bit and the cache does not change at all, because it has its own precision.

A configuration-file trap

Some guides compute head size as hidden_size ÷ num_attention_heads. That is the right fallback only when the configuration does not list head_dim, as with Llama 3.1 70B. For many current models it gives the wrong answer: Qwen3-32B's hidden size divided by its 64 heads is 80, but its head_dim is 128. The shortcut also fails for Qwen3-30B-A3B, Gemma 3, Mistral Small and gpt-oss. When the configuration lists head_dim, use it. [1]

The biggest savings happened before you downloaded the model

Take Qwen3-32B once more. It has 64 attention heads that ask questions of earlier tokens, but only 8 KV heads that store answers. Groups of eight heads share one set of keys and values. If every head kept its own, as in the original transformer, the same 32K conversation would need 64 GiB of cache instead of 8.

That sharing has a short history. In 2019, Noam Shazeer proposed multi-query attention, in which every head shares a single key and value set. In his translation experiments, decoding time per token fell from 46 to 3.8 microseconds, at a small cost in quality: the BLEU translation score went from 26.7 to 26.5. [2] In 2023, Ainslie and colleagues proposed grouped-query attention as the middle ground: a few shared sets instead of one. With eight groups, their model ran nearly as fast as multi-query (0.28 against 0.24 seconds per sample, where full multi-head attention took 1.51) and scored nearly as well as multi-head (47.1 against 47.2), and existing models could be converted with about 5 percent of their original training compute. [3] Most open models you will download today use it.

DeepSeek went further with multi-head latent attention: each layer stores one compressed vector per token and reconstructs keys and values from it when needed. [4] [5] The DeepSeek-V2 paper reports a cache 93.3 percent smaller than its earlier 67B model's. That figure includes storing the cache at about 6 bits per number; by my arithmetic from the published configurations, the architecture alone accounts for roughly an 82 percent reduction at equal precision. [4]

Sliding windows attack the length instead. In Gemma 3, five of every six layers look back only 1,024 tokens, so their cache stops growing; only the remaining layers keep the long view. gpt-oss alternates layers with a 128-token window and full-attention layers. [1]

The practical consequence: the memory price of long context is a design decision made by a model's architects. If long documents matter to you, put the per-token cache cost on your comparison list next to benchmark scores.

You pay for the context you reserve, not the context you use

Many runtimes set aside the cache for the whole configured context when a model loads, whether or not a conversation ever gets that long. On busy servers this used to waste most of the memory. When the vLLM team measured their re-implementations of an earlier serving system, Orca, only 20.4 to 38.2 percent of the memory reserved for the cache actually held token data. Their PagedAttention design allocates the cache in small blocks on demand, the way an operating system manages memory; in the same measurement, 96.3 percent of vLLM's cache memory held token data, and it served two to four times as many requests at the same latency. [6]

At home, the lesson is about settings. Two of them multiply the reservation:

  • Context length. Ollama now picks a default from your GPU memory: 4K tokens below 24 GiB, 32K from 24 to 48 GiB, and 256K above that, capped at what the model supports. On a 24 GiB card that default is 32K, which, as the chart above shows, does not fit beside Qwen3-32B's weights. Ollama's documentation also recommends at least 64,000 tokens for agents and coding tools, and its FAQ still quotes an older 4,096 default, so check what you actually got. [7]
  • Parallel requests. Ollama's memory need scales with OLLAMA_NUM_PARALLEL × context length: four parallel slots at 8K reserve like one 32K conversation. In llama.cpp's server, an explicit -np 4 with -c 32768 splits the context into four 8K slots, while the default automatic setting gives four slots that share one pool. [7] [8]

The formula shows exactly which knobs exist, and each one gives up something different.

Cache quantization is the lever most local users can pull today. Ollama's OLLAMA_KV_CACHE_TYPE accepts f16, q8_0 or q4_0. Its documentation describes q8_0 as using about half the memory with a very small quality cost, and q4_0 about a quarter with a small to medium cost that grows with context; models with many query heads per KV head, such as Qwen2, may lose more precision. The setting applies to every model the server loads, and it requires Flash Attention, a faster way of computing attention that Ollama enables where the hardware supports it. [7] llama.cpp exposes the same choice through --cache-type-k and --cache-type-v, and turns on Flash Attention itself when a quantized value cache needs it. [8] One caution from its documentation: heavy cache quantization can substantially degrade tool calling, so retest an agent after changing it. [9]

Research suggests the bits can go lower. KIVI, from Liu and colleagues, stored the cache at 2 bits. Its trick was to notice that keys carry a few unusually large numbers in the same slots of the vector for every token, while values do not, so it compresses keys slot by slot and values token by token. For Llama-2-7B that cut peak memory, weights included, by a factor of 2.6. [10]

Eviction has a surprising wrinkle. Xiao and colleagues found that if you keep only a rolling window of recent tokens, many models fall apart as soon as the conversation's first tokens are evicted. They measured perplexity, roughly how many equally likely next tokens the model is torn between, where lower is better. With a 1,024-token window alone, Llama-2-13B scored 5,158 on a long book. Keeping just the first four tokens beside a 1,020-token window brought it back to 5.40. The reason: attention must add up to 100 percent, so models learn to park the surplus on the first positions, which the authors call attention sinks. Their StreamingLLM method lets a model keep generating over millions of tokens with a fixed cache, but it cannot recall anything that was evicted. [11]

Low-rank compression keeps every token but stores smaller vectors. Eigen Attention, from Saxena and colleagues, cut the cache by up to 40 percent. It also shows why memory and speed must be measured separately: on one Llama-3-70B layer, the compressed version ran 8 percent slower because of extra work around positional encoding, the part of the model that tracks word order. [12]

Check what your runtime actually reserved

Your runtime can show you what it actually reserved. With Ollama, ollama ps lists each loaded model's size, where it is running (GPU, CPU or a split), its context and when it will be unloaded. [7] Compare that context with the one you meant to set, and the size with your calculation. A CPU/GPU split means weights and cache together did not fit on the card. If the numbers disagree with your arithmetic, look for parallel slots, a different cache precision, or another program holding memory before you change the arithmetic to fit the observation.

[OPINION] I would set the context for the longest document I actually send, plus room for the answer, and no more. For an agent, the whole running transcript counts, which is why Ollama suggests at least 64K for agents and coding tools. But reserving 128K tokens of cache for conversations that never pass 8K is the easiest way to run out of memory through configuration rather than hardware.

Price your own model in five minutes

Find your model's layer count, KV heads and head size. Multiply them together, then by 4, to get bytes per token at 16 bits. Multiply by your context length and add the weight file's size. For Gemma 3, gpt-oss and DeepSeek, use the table instead; the simple formula overstates them. If the total is close to your memory, try the next context size down or an 8-bit cache, and confirm the result with ollama ps or your runtime's log.

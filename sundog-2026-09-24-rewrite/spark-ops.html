Find What's Using Your DGX Spark's Memory

On a unified-memory machine, the usual GPU memory readout goes blank. Here is how to find the process, service and setting that is holding the memory, and what to change.

By Sundog

Rewritten 24 September 2026

For DGX Spark owners with terminal access · Also useful on any shared Linux AI machine

A model that loaded fine yesterday fails today with an out-of-memory error. You run nvidia-smi to see what is using the GPU's memory, and the answer is Not Supported.

That message is not a fault, and it is not an all-clear. It is the first clue to how this machine is built, and once you understand it, finding the memory's owner takes a few minutes with ordinary Linux tools.

On a Spark, the GPU shares the computer's memory

A typical desktop GPU has its own memory, separate from the computer's. The DGX Spark does not. Its GB10 chip combines the CPU and GPU, and both use one pool of 128 GB of LPDDR5x memory, which NVIDIA describes as coherent unified system memory. [1] The operating system, your containers, your model servers and the GPU's work all draw from the same 128 GB.

That is why the familiar readout goes blank. NVIDIA's known-issues page says the aggregate Memory-Usage field in nvidia-smi reports "Not Supported" on this integrated GPU, which has no dedicated framebuffer, while memory used by individual GPU processes is still listed. [2] On an integrated GPU, nvidia-smi documents that per-process figure as system memory. [3]

On unified memory, "what is using the GPU's memory?" becomes "what is using the machine's memory?" Ordinary Linux tools can answer most of that question.

One more subtlety from the same NVIDIA page: CUDA's own free-memory query can report less than is really available, because it does not count memory Linux could free up by moving pages to swap. NVIDIA's guidance is to read the operating system's figures instead, such as MemAvailable in /proc/meminfo. [2] A program that sizes itself from CUDA's figure can therefore see less memory than the machine can actually provide.

The three usual suspects

On a shared AI machine, memory that seems to vanish usually belongs to one of three things. Each shows up differently, and each is fixed in a different place.

1. A server that reserved memory before anyone asked

Some model servers claim a fixed share of memory when they start, however busy they turn out to be. vLLM is the clearest example. Its gpu_memory_utilization setting is the fraction of GPU memory an instance may use, and vLLM allocates its attention cache (the KV cache, as logs and settings call it) from that share up front. The default is 0.92 as of version 0.20.0, released in April 2026, and was 0.9 before that. [4] On a machine with its own graphics memory, that is a reasonable default. On a Spark, the same fraction applies to the pool the whole system shares: at 0.92, one vLLM instance may claim over nine-tenths of the memory that everything else also needs.

NVIDIA's own Spark instructions account for this. Its vLLM playbook uses 0.8 to leave headroom, and its Nemotron playbook describes 0.8 as the share of unified memory vLLM may take, with advice to lower it toward 0.70 after an out-of-memory error, which returns memory to the operating system at the cost of a smaller cache. [5] llama.cpp's server behaves similarly in a quieter way: it reserves the KV cache for its whole context when it loads, and if you do not pass -c, it starts from the model's own maximum context and trims only as far as needed to fit. [6] The calculation for that cache is in Why a Longer Chat Needs More Memory.

2. A model kept warm

Ollama keeps a model loaded for five minutes after its last request by default, so the next question is answered quickly, and by default it can hold several models at once: three per GPU. A keep_alive of -1, set by someone months ago, keeps a model loaded indefinitely. ollama ps lists what is loaded and, in its UNTIL column, when each model is due to unload. [7]

3. Linux's file cache

Linux keeps recently read files in otherwise unused memory, because rereading them from disk is slow. A model file you just loaded is exactly that kind of file, and it can be tens of gigabytes. The kernel normally gives this memory back when a program needs it, which is why free -h counts reclaimable cache in its available column rather than as used. [8]

On a Spark, some programs do not count that cache as available. NVIDIA's playbooks note that some applications are not yet aware of unified memory, so memory problems can appear even when usage is within capacity, and its knowledge-graph playbook describes exactly this with Ollama when switching between models. NVIDIA's documented debugging workaround is to flush the cache and then restart the application:

sudo sh -c 'sync; echo 3 > /proc/sys/vm/drop_caches'

It only discards clean cached copies of files, so it loses no data. It does need administrator rights, and it slows everyone's next file reads, which is why the Linux kernel documentation advises against using it outside testing and debugging; on a shared machine, ask first. [2] [5] [9] Treat it as a diagnosis, not a routine: if free -h shows the buff/cache figure dropping by tens of gigabytes and the restarted application now loads, the cache was in the way.

Trace the memory to its owner

These are standard, read-only inspection commands. They change nothing, but some output, such as process arguments and logs, can contain paths, tokens or other private details, so review it before sharing.

Step 1: How much is really available?

free -h
ps -eo pid,user,etime,rss,comm --sort=-rss | head -n 15

In the free -h output, read the available column, not the free column. Available includes cache the kernel can hand back; it is the MemAvailable figure NVIDIA recommends. The ps list shows the processes holding the most resident memory, with their owners and how long they have been running. Adding up those rows will not reproduce the total exactly, because memory can be shared between processes. [8]

Step 2: Which processes are using the GPU?

nvidia-smi
nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv

The second command lists each GPU process with its memory use. On a Spark, expect per-process values here even though the overall memory line says Not Supported. [2] [3]

Step 3: Which service owns the process?

ss -ltnp
ps -p 1234 -o pid,ppid,user,lstart,etime,rss,args

ss -ltnp lists listening network ports with the process behind each one. Find the port your AI application talks to. Then replace 1234 with a process ID from this step or Step 2 to see its owner, start time, full command line and, in the PPID column, the process that started it. The process on the port may be a proxy, or a launcher such as Ollama's server, which runs each model as a separate llama-server process. If the process column is empty, it usually belongs to another user; sudo ss -ltnp shows it. [8]

Step 4: Is it a system service or a container?

systemctl status 1234
journalctl -u UNIT_NAME --since today --no-pager
docker ps --no-trunc
docker top CONTAINER_NAME
docker logs --tail 100 CONTAINER_NAME

systemd is Linux's service manager. systemctl status with a process ID names the service that process belongs to, and journalctl shows that service's log, which connects it to the configuration that launched it. [10] On a Spark, many AI workloads run in Docker, since NVIDIA's container runtime comes preinstalled for GPU access. [11] docker ps lists container names, and docker top shows a container's processes with their host process IDs, which you can match against Step 2. [12]

Step 5: What did the server decide to reserve?

Once you have the owner, find the setting that sized its memory: ollama ps for loaded models, contexts and unload times; the --gpu-memory-utilization and --max-model-len arguments of a vLLM command line; the -c and -np arguments of llama-server. The startup log usually states how much memory the KV cache took.

Change the setting, not just the process

Once its owner confirms a workload is no longer needed, stop it through whatever launched it: systemctl stop for a service, docker stop for a container, ollama stop for a loaded model. Killing a worker process directly often achieves nothing, because a supervisor restarts it with the same settings.

Then fix the reservation so the problem does not return. Lower vLLM's memory fraction or its maximum context. Give Ollama a shorter keep_alive or a lower OLLAMA_MAX_LOADED_MODELS. Set llama-server's context explicitly. NVIDIA's own knowledge-graph playbook for the Spark, for example, sets OLLAMA_MAX_LOADED_MODELS=1 and an 8-bit KV cache, while keeping models loaded for 30 minutes: it limits how many models are resident at once, not how quickly one unloads. [5] After each change, repeat the failed load once, and write down the change and the result.

[OPINION] A shared machine runs best when every long-running model service has a written record: who owns it, its port, its container or unit name, the model it serves, its memory setting, and how to stop it. Six lines per service. It turns an out-of-memory error from an investigation into a lookup, and it lets you ask the owner before you stop something they still need.

Make the occupancy record today

Run steps 1 to 4 once while the machine is healthy, and write those six lines for each model service you find. The next time a load fails, compare the live output with that record before changing anything.

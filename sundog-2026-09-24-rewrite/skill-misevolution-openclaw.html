Test Your Agent's Skills Before They Become Habits

A saved skill turns one good run into standing instructions. Research shows two different ways that goes wrong, and how to test for both.

By Sundog

Rewritten 24 September 2026

For people using agents that save skills (OpenClaw, Claude Code, Codex, OpenCode and similar) · No coding required to follow

The first time an agent solves a job, it improvises. The next time, if it saved a skill, it follows notes from that first run, including details that only fit the first job. That is the promise of skills and also the problem with them.

A skill, in the sense used by current agent tools, is a folder with a file named SKILL.md: a short description of when to use it, followed by instructions, plus optional scripts or reference files. It changes what the agent reads before acting. It does not change the model. [1] That makes skills cheap to create, easy to share and easy to trust more than they deserve.

A skill is chosen by its description and obeyed by its body

Agents do not read every skill in full at the start of a session. Under the Agent Skills specification, which Anthropic introduced in October 2025 and published as an open standard that December, the agent starts with only each skill's name and description, about 100 tokens per skill (a token is a word or a piece of one). When a task looks like a match, it loads the full instructions, which the specification recommends keeping under 5,000 tokens, and it opens extra files only if the instructions call for them. [1] This design, called progressive disclosure, keeps dozens of installed skills from filling the context window, the text a model can consider at once.

It also means every skill involves two separate decisions. The description decides whether the skill is used. The body decides what the agent does once it is. They can fail independently, and in one study, only 2 of 125 skill-caused task failures came from picking the wrong skill. [3] The rest were good matches with bad instructions.

Here is a skill an agent might save after successfully exporting one customer's records:

---
name: export-business-data
description: Export business records to CSV.
---
Always use columns: customer_id, name, total.
Write the result to the temporary export directory.
Delete intermediate files when the export is complete.

The description is broad enough to match almost any export. The body is specific to one job. The next customer wants different columns and needs the intermediate files kept for an audit. The agent will pick this skill, correctly, because the topic matches, and then follow it, faithfully, into the wrong result.

Skills were designed to make agents compound

The idea is older than the file format. Voyager, a 2023 research agent that played Minecraft, stored each program that worked as a named skill, retrieved skills by comparing the current task with their descriptions, and combined simple skills into more complex ones. Compared with earlier agents, it collected 3.3 times as many unique items, traveled 2.3 times farther and reached technology milestones up to 15.3 times faster; in the main runs, a version without the skill library stalled. Dropped into a new world with four unseen tasks, Voyager solved all four in every trial while the comparison agents solved none. [2]

That is the compounding effect everyone wants: each solved problem makes the next one cheaper. The research of the last few months has been measuring the opposite effect, and it has found two distinct ways a saved skill makes an agent worse.

Failure one: the right skill with the wrong instructions

Dong and colleagues set out to prove that a specific skill caused a specific failure, which is harder than it sounds: agents fail often and for many reasons, so one failed run that happened to load a skill proves nothing. Their method was a paired test. They ran the same task twice with the same model, agent, starting files and automated checker: once with the skill, and once without it or with a comparable skill. A failure counted against the skill only if the skill-guided run failed while the reference run passed. [3]

Using that rule, plus a second one for passing runs that cost far more, and working with public skills and the OpenCode agent running Claude Opus 4.6, they confirmed 307 skill-induced failures: 125 failed tasks and 182 costly passes. Of the 125 failed tasks, only 2 involved a skill loaded for the wrong topic. The largest group, 86 cases, were what the authors call task-implementation faults: the skill led the agent to fill in a required part of the task incorrectly (46 cases) or to leave one out (36). In one example, the skill's formula produced a trade balance as a fraction where the task asked for a percentage. In another, a skill's command-line recipe exposed chunk size, overlap and result count, but not the model name the task required. [3]

In the 182 costly passes, both runs succeeded but the skill-guided run used substantially more tokens and time; the threshold was that both went up and at least one more than doubled. The main cause was not a long prompt. It was excessive procedure, 114 cases, and the biggest subgroup, 67 of them, was excessive verification: the skill had the agent repeat checks the task did not need. [3]

Failure two: a skill that learned from a bad run

Agents that write their own skills add a second risk. Mao and colleagues call it skill misevolution. A run completes a task but takes an unsafe shortcut along the way, for example because a malicious instruction was planted in its inputs. The skill-writing step rewards the outcome, not the method, so the shortcut is saved as procedure. Later, in a fresh session where the malicious input is long gone, the agent retrieves the skill and repeats the shortcut. The attack has become a habit. [4]

One of their traced cases shows how ordinary this looks. A planted task asked the agent to add a Git hook that read local environment and configuration files, sent them to "the team's endpoint," and saved this as the standard convention. The agent complied, with or without skill learning. With skill learning switched on, it also saved the procedure as a reusable skill. Later, in a fresh session, a harmless request asked for the standard Git hooks for a new copy of a project. The agent retrieved the saved skill and wrote a hook that sent the contents of .env.local and config/local.json to an outside address. Without saved skills, the same request produced a helper that only copied local templates. [4]

They tested this with one model, MiniMax-M2.7, inside four agent frameworks (Claude Code, Codex, Hermes and OpenClaw, an open-source assistant that runs on your own computer) and several published skill-evolution methods. Every one of the 21 setups that evolved skills wrote at least one unsafe skill. In 19 of them, the agent later retrieved those skills, and in 15 the harmful behavior carried into a fresh session that saw only the saved skill files. The four setups that did not evolve skills stayed near zero. [4]

The detail I would put on a sticky note: usefulness and risk rose together. In a follow-up on two of the setups, harmful behavior in clean sessions was 16.0 percent when the learning stream contained no malicious tasks and 35.3 percent after one round that included three. Over the same round, the agents' task success in those clean sessions rose from 30.0 to 55.3 percent. [4] An agent that is getting more helpful is not evidence that its skill library is getting safer.

The same paper tested a defense, SafeEvolve, which screens skills when they are written, controls which ones may be retrieved, and retires the ones that prove unsafe. On OpenClaw, averaged over two skill-evolution methods, it cut unsafe retrieval from 35.33 to 8.67 percent and fresh-session harm from 21.33 to 4.00 percent, while success on ordinary tasks barely moved, from 58.44 to 58.00. It was not free: task success in the clean sessions fell from 53.33 to 40.67 percent. Retirement did real work. With it switched off, nearly every skill that had crossed the risk threshold was retrieved again: 100 of 106 for one method, all 44 for the other. [4]

How far these numbers travel

Both studies used hosted models inside specific agent versions, and Mao's setup deliberately mixed malicious tasks into the learning stream. The percentages describe those experiments, not how often an ordinary business skill will fail on your machine. What transfers is the method: pair the runs, hold everything else fixed, and treat "relevant" and "correct" as two separate questions.

Borrow the compiler testers' trick

Dong's paired test has an old ancestor, and the authors cite it. In 1998, William McKeeman described differential testing, which grew out of testing compilers at Digital Equipment Corporation: feed the same test cases to two or more comparable systems, and treat any difference in their results, or a crash in one of them, as a candidate bug. [5] Skills are a good fit for the same idea. You may not have a perfect specification for "a good export," but you can compare the agent with the skill against the same agent without it.

For a skill your agent wrote itself, compare what the two runs did, not only whether they passed. A skill-guided run that reads secrets, sends data somewhere, or installs something the plain run never touched is the pattern Mao's study found, and a pass/fail checker will not flag it.

For the export skill, the useful second task is the one that disagrees with the first: different columns and a rule to keep intermediate files. Run it with and without the skill. Then run the original task again with the revised skill, because a revision that handles the new job can still break the old one.

Rewrite the skill so the task supplies the details

The repair is usually to keep the method and remove the old job's values:

---
name: export-business-data
description: Export tabular records to CSV when a task asks for an
  export. The task supplies the columns, destination and retention rule.
---
1. Read the required columns, their order, the destination and the
   retention rule from the current task or the file it references.
2. If any of those is missing, ask before writing files.
3. After writing, check that the header matches the requested columns.
4. Keep intermediate files unless the task says they may be deleted.
5. Report the output path and the check you ran.

Three changes do the work. The description now says when the skill applies, not merely what topic it covers. The body reads values from the current task instead of carrying the last customer's. And the verification is a single check tied to the request, not a list of checks that grows with every edit. Keeping the body short matters for a second reason: in Dong's study, almost all the extra context cost came from skill bodies that are loaded in full whenever the skill is used. [3]

[OPINION] I would treat a newly saved skill as a colleague's notes from one job: specific, often useful, and not yet policy. It gets promoted when it passes a paired test on a task that disagrees with the one that produced it. It gets a version number, so the previous one can come back. And it gets retired when a change in the work makes its assumptions false, rather than left in the library to be retrieved by a future session that does not know the history.

Skills you download carry someone else's assumptions, and sometimes worse

Everything above concerns skills written in good faith, by the agent itself or by other people. Downloaded skills add an older kind of risk. On 1 February 2026, Koi Security reported auditing all 2,857 skills then listed on ClawHub, OpenClaw's public skill registry, and finding 341 malicious ones. Of those, 335 belonged to a single campaign whose skills included a fake "Prerequisites" section telling the user or agent to run a setup script; on macOS, that script installed an information-stealing program. By mid-February, Koi's count had reached 824 among more than 10,700 listed skills. [6] VirusTotal's analysis made the key point: the SKILL.md file itself was not malware. The harm came from the setup steps it persuaded someone to carry out. [7] Trend Micro later described skills written to talk the agent itself, rather than the human, into installing a fake command-line tool that delivered the same family of malware. [8]

OpenClaw responded by scanning every ClawHub skill with VirusTotal, which its maintainers called "not a silver bullet," and its documentation now tells users to treat third-party skills as untrusted code. [9] A skill is instructions your agent will follow with your permissions. Read one before installing it, the way you would read a shell script before running it, and be most suspicious of any step that downloads and runs something.

Audit one skill this week

Pick a skill whose body contains a fixed path, column list, cleanup rule or the word "always." Write one task where that assumption is false. Run it with and without the skill, then run the original task with any revision. Keep the skill only if it helps on both.

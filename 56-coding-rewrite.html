Best Local LLMs for Coding in 2026: Picks for 8 GB, 16 GB, and 24 GB of VRAM

Updated: August 27, 2026

Fit and serving compatibility decide the tier. Comparable benchmark results rank the 24 GB candidates; the other tiers lack matched comparisons.

A published coding score measures a particular endpoint, serving configuration, and harness; a local Q4 deployment is a different configuration. The current picks are Ornith-1.5 9B for 8 GB, GPT-OSS 20B for 16 GB, and Qwen3.8 27B for 24 GB. Only the 24 GB tier has a like-for-like published comparison; the cited evidence provides no matched ranking for the other two tiers.

What changed as of August 27, 2026?

The former 24 GB recommendation, Qwen3-Coder 32B Dense, is no longer listed because both proposed owner ids return 401 and Qwen's public Coder collection and pinned size table omit it; whether a private checkpoint exists remains unknown.[1]

What is the best local coding model for 8 GB of VRAM?

Pick: Ornith-1.5 9B. Its owner Q4_K_M file is 5.780 GB. FP16 KV cache brings the total to 6.05 GB at 8K and 6.85 GB at 32K. The same calculation reaches 14.37 GB at the native 262K window, beyond this tier.[3]

The repository is ungated and the owner supplies the GGUF. The card's YAML declares MIT, but the repository's LICENSE file does not resolve. Tool calling: Not established by the sources used here.[3]

No coding benchmark for Ornith-1.5 9B appears in the available primary-source record. This pick rests on fit and fetchability; the cited evidence supplies no same-card, same-harness comparison against another 8 GB candidate.

What is the best local coding model for 16 GB of VRAM?

Pick: GPT-OSS 20B. The model card lists 21B total parameters with 3.6B active, Apache 2.0, native function calling, structured outputs, and a vendor claim that the MXFP4 weights run within 16 GB. The ggml-org MXFP4 file is 12.110 GB. With FP16 KV, the calculated totals are 12.31 GB at 8K, 12.92 GB at 32K, and 15.33 GB at the native 128K. A 16 GiB card holds 17.18 decimal GB, leaving 1.85 decimal GB before runtime overhead at the native context.[4]

Owner-published GGUF: none. The available ggml-org artifact keeps the model's native MXFP4 format, and llama.cpp has a built-in gpt-oss architecture and server preset. vLLM 0.28.0 lists GptOssForCausalLM with the openai tool parser.[4][9]

OpenAI's paper self-reports 60.7 on SWE-bench Verified for GPT-OSS 20B at high effort with a Codex-CLI-like exec and terminal scaffold. NVIDIA independently measures 52.44 on SWE-bench Verified with NeMo Evaluator. The 8.26-point gap belongs to two different harnesses and should remain unaveraged; it shows why the evaluation and serving details must travel with the score. The cited sources provide no same-harness comparison against another 16 GB candidate, so these results supply context rather than a tier ranking.[5]

What is the best local coding model for 24 GB of VRAM?

Pick: Qwen3.8 27B. The owner checkpoint is ungated and Apache 2.0. The ggml-org Q4_K_M file measures 18,973,870,432 bytes, or 18.974 GB. With FP16 KV, weights plus cache total 19.51 GB at 8K, 21.12 GB at 32K, 27.56 GB at 128K, and 36.15 GB at the native 262K. A 24 GiB card holds 25.770 decimal GB, so the 32K configuration leaves 4.65 decimal GB before runtime overhead; the two longer contexts exceed the card.[2][8]

Owner-published GGUF: none. ggml-org publishes the Q4_K_M build with llama.cpp's qwen35 architecture, and Qwen points local users toward SGLang, vLLM, and TokenSpeed. MLX and Ollama conversions exist for the same 27B family.[8]

When FP16 KV blocks the required context, q8_0 KV brings 128K inside the card before overhead. More aggressive KV formats demand caution: llama.cpp warns that extreme KV quantization such as q4_0 can substantially degrade tool calling.[9]

Qwen self-reports 73.0 on Terminal-Bench 2.1 with Terminus and 61.7 on SWE-bench Pro with Claude Code at a 256K evaluation context. On the same card and under the same harnesses, Qwen3.6 27B scores 63.4 and 53.5, respectively. Qwen3.6 also clears the 24 GB tier at 8K and 32K under the same catalog arithmetic, so this like-for-like comparison ranks Qwen3.8 ahead within the tier. These published runs do not describe the 32K Q4 desk configuration above.[2]

What changes above 24 GB?

Qwen3-Coder-Next 80B-A3B begins above this range. Its owner Q4_K_M shards total 48.411 GB, and 8K FP16 KV raises the total to 48.61 GB before overhead. Qwen's technical report gives SWE-bench Verified results ranging from 70.6 to 71.3 across SWE-Agent, MiniSWE-Agent, and OpenHands. That 0.7-point spread shows scaffold choice was a small variable for this model in that experiment.[6]

What do coding benchmark scores actually measure?

Artificial Analysis Intelligence Index v4.1.1 runs evaluations through APIs. Its agentic components use named harnesses: Stirrup for GDPval-AA v2, the original tau2-bench harness for banking tasks, and Terminus 2 in an E2B sandbox for Terminal-Bench v2.1. A displayed composite therefore belongs to an evaluated endpoint and test stack.[7]

The Endpoint Accuracy Index exists because identical weights vary by provider. Its GPT-OSS 120B composites span roughly 70% to 101% of a self-hosted reference. Artificial Analysis attributes the spread to quantization, sampling defaults, context handling, token limits, prompt parsers, and other endpoint-side configuration. This provider spread is the evidence for treating a hosted score as endpoint-specific; the 0.7-point scaffold spread above supplies no such support.[10]

The reference uses vLLM or SGLang at the highest recommended precision, with worked runs on eight NVIDIA B200 GPUs. The Intelligence Index and Endpoint Accuracy methodology pages never name llama.cpp.[10]

Artificial Analysis publishes llama.cpp results in a separate Mobile Device Benchmark Set using Q4_K_M or smaller GGUFs at 16K. Its methodology explicitly says those scores can differ from the same model's results elsewhere on the site.[11] The practical use of leaderboard numbers is narrow: compare named variants under the same benchmark version and scaffold, within a tier that already fits.

What must the runtime support for local coding?

A coding workflow needs the model format, the correct template or parser, and the required endpoint. llama.cpp v0.3.0 exposes POST /infill, but FIM works only when the loaded GGUF contains the required special tokens. Its server exposes function calling through templates and a generic fallback. vLLM requires automatic tool choice plus the parser matched to the model family.[9]

GPT-OSS requires the Harmony message format; serving it without Harmony can produce degraded or malformed output without an error. A bare llama.cpp -hf load is also hazardous here: the loader defaults to Q4_K_M and silently falls back to the first repository file when that quant is absent, while the ggml-org repository contains an MXFP4 model and Eagle3 draft-model files. Name gpt-oss-20b-MXFP4.gguf explicitly.[4][9]

The StarCoder2 7B card documents FIM training. With no owner GGUF or supported download path documented, it is excluded from the picks. A community conversion becomes usable for infill only when its GGUF carries the model's FIM tokens.[9][12]

How were the picks assembled?

Model existence, licenses, contexts, formats, and runtime claims come from owner cards or pinned runtime documentation. Named benchmark results retain the publisher, precision, version, and harness. The Ornith weight input is measured from its owner GGUF file; GPT-OSS MXFP4 and Qwen3.8 Q4_K_M inputs are measured from ggml-org file bytes, and neither is an owner-published GGUF. FP16 KV additions are arithmetic from the published configurations. Hybrid-model linear or Mamba state remains outside those totals when no occupancy figure is available.

Fix the Tool Loop Before You Replace the Model

Hold the model fixed and diagnose invalid actions, retries and unused tool results. Harness research supports a concrete interface experiment, not an untested GPU buying rule.

By Sundog

6 September 2026

If your coding agent keeps calling a tool with the wrong arguments, downloading a larger model is an expensive way to avoid inspecting the tool call.

The useful question is specific: did the model choose the wrong action, did the interface make a valid action hard to express, or did the agent fail to use the result? Those failures can look identical in a final score. They leave different traces.

[OPINION] I would freeze the model and repair a repeatable interface failure before changing weights. A narrow fix gives you a comparison you can trust. It also lets the next model inherit an interface that already works.

Find the first failed transition

Take an illustrative repository-editing run. The agent finds the right file, prepares a plausible patch and sends the tool a string where the schema requires an array. The tool rejects it. The agent repeats the same call, then reports that editing is unavailable.

The failed patch and the failed interface are different things to test. A validator can identify the wrong field before dispatch. A precise error can show the expected type. A retry can carry the failed arguments and the actual error back to the model. Each change has a visible purpose; none requires pretending that the patch itself was correct.

Keep the original task and model settings fixed. Try the interface change on the failing case, then on untouched cases with valid calls, missing fields and different errors. If the intervention merely hard-codes the answer to the first trace, it has taught you very little.

The research changes the place to look

Life-Harness treats the interface around a frozen model as something that can be improved across task settings. It reported improved performance in 116 of 126 model-environment settings. That supports investigating the harness as a source of performance differences; it does not establish a preferred coding-model quantization on a desktop GPU. Life-Harness, arXiv:2605.22166v1.

Self-Harness also studies changes around the model. Its local Qwen deployment used four H200s. The word local describes deployment location, with no promise about reproducing that workload on a 24 GB card. Self-Harness, arXiv:2606.09498v1.

HELIX reports a code-repair evolution round with a 65-candidate portfolio and 438 records from a 200-slot slice. A searched portfolio, the selected fixed harness and its baseline cover different experimental objects. A reader cannot turn the portfolio's coverage into the score of one installed agent. HELIX, arXiv:2608.13951v1.

I did not test these systems on a local coding workload. Their shared value for this decision is that weights can remain fixed while the surrounding procedure changes. The magnitude of your improvement still comes from your tasks.

Count the loop once

A harness has costs, but there is no inherent two-to-four-gigabyte GPU charge for validating arguments and keeping a task record. Host-side orchestration, a separate resident model and a longer generator context are different allocations.

Tool output returned to the generator can lengthen the prompt. Repeated calls can lengthen it again. On a conventional attention model, those retained tokens affect cache requirements; a runner may also reserve the cache in advance. Count that context in the generator's budget once. If your harness runs another model, name its artifact and residency separately. The KV geometry guide works through the arithmetic.

Neither a longer trace nor the agent papers settles a 7B Q8 versus larger-Q4 purchase. That comparison needs the actual artifacts, runtime and completed coding tasks. The coding-model guide is a starting point for selecting candidates after the interface has a fair test.

Keep useful errors small

The right correction is often less text. A parser rejection needs the field and expected type. A test failure needs the failing test and relevant output. Sending the entire tool history on every retry spends context without establishing that the model used it.

For the malformed-array example, compare completed patches, repeated invalid calls, elapsed time and retained prompt length. Keep successful calls in the test set too: a check that catches one error while blocking normal work has moved the failure.

Store the task result beside the model revision and harness revision. Once you have a repeatable improvement, consider whether part of the procedure belongs in a reusable skill. That introduces a separate promotion decision; a successful run leaves the scope of later reuse unresolved.

Then change the model if the remaining failures justify it. You will be comparing two models through the same repaired interface, with the failed transitions still visible.

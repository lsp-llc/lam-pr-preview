Keep Retrieval Small Enough to Earn Its Place

Compare embedding-model residency and retrieved-token KV separately, using exact artifacts and one fixed generator. Test recall, latency and context costs.

By Sundog

6 September 2026

A retrieval stack can use the same GPU in two different ways: the embedding model occupies memory while it is resident, and the passages you return occupy context while the generator reads them. Changing one does not automatically fix the other.

[OPINION] I would start with the cheapest retrieval setup that reliably finds the needed passage, then spend more only on the questions it misses. A small dense retriever can coexist with a larger generator. A lexical index can be enough for exact identifiers. Neither choice earns its place by being fashionable.

The useful tradeoff is retrieval recall and latency against residency and context. Test those costs separately. Otherwise a comparison can quietly swap the generator, embedding model, chunk length and passage count, then blame one of them for the result.

Hold the generator still

Use Qwen3-14B for a concrete planning example. Its official Q4_K_M file is 9,001,752,960 bytes, or 8.3835 GiB. Its 40 layers, 8 KV heads and 128-dimensional heads give an ordinary FP16 attention cache of 160 KiB per token. One GiB here means 1,073,741,824 bytes. Exact artifact; model configuration.

Reserve 1,024 tokens for the system message and question, and 512 for the answer. Those are chosen example lengths, with no earlier conversation. Compare five 2,048-token passages with three 384-token passages. The first retrieval adds 10,240 tokens; the second adds 1,152. Including the fixed 1,536-token allowance, calculated KV is 1.7969 GiB and 0.4102 GiB respectively.

These are incomplete storage budgets, with no measured fit or quality ranking. Embedding activations and scratch space, generator workspaces, allocation padding, other processes and any extra reserved context are excluded. Loaded tensors can differ from disk bytes. Compare actual peak allocation with the memory your device reports as available before choosing a context. I did not test these stacks on a 16 GB card.

The larger dense model costs about 2.07 GiB more in this weight comparison. The longer retrieval costs about 1.39 GiB more in this generator's calculated KV. Those are separate choices: a large embedder can return three short passages, and a small one can return five long ones. No row proves that a particular embedder requires its chosen chunk budget.

Make the missing passage identify the next change

Take a question your system answered incorrectly and inspect the passages actually sent to the generator. An embedding model's retrieval training does target relevance. Nomic describes search-query/answer finetuning; Qwen documents retrieval tasks and query instructions. That training still cannot guarantee that your required version, date or answer-bearing sentence appears in the selected chunks. Nomic training; Qwen retrieval instructions.

A missing exact part number suggests testing lexical or hybrid retrieval. A correct topic with the wrong policy revision suggests an explicit metadata filter. A passage that ends immediately before the answer suggests changing chunk boundaries or expanding a selected span. Each failure points to a smaller experiment than replacing the whole stack.

Keep the generator and answer prompt fixed while trying that change. If the necessary passage reaches the prompt and the answer remains wrong, the investigation moves to how the generator uses it. More retrieved text alone has supplied no explanation.

[OPINION] For a small local trial, I would choose ten real questions and record the needed source span before tuning. Ten keeps the first trial manageable; no validated acceptance threshold follows from that choice. Include identifiers, paraphrases, conflicting versions and one question the collection cannot answer. Keep some additional questions untouched until choosing a configuration.

The index can stay outside the GPU

Document embedding and query embedding have different schedules. You can build an index ahead of time, then encode only the live query. A CPU embedder leaves its weights out of GPU residency; a sequential GPU setup can unload it before loading the generator. Both change latency and host-memory use, which still need measurement. They do not remove the generator's cost of reading returned passages.

For scale, 50,000 vectors with 768 F32 components occupy 153,600,000 bytes, about 0.143 GiB, before graph links, IDs, text, metadata and allocator overhead. Here 768 is a deliberately chosen output dimension. Qwen3-Embedding-4B supports a larger maximum output dimension, so use the dimension you actually encoded rather than copying this estimate into another index. Qwen dimension support; FAISS storage guidance.

This example keeps search on the CPU. Moving an index to a GPU requires a supported index type and adds its allocations to the budget. Ordinary HNSW and the documented FAISS GPU Flat/IVF implementations are different choices. FAISS GPU index support.

Keep provenance even when the answer feels familiar

Public information can still deserve retrieval. A current release note, a changed licence, or a source the reader needs to cite has value beyond whether the model remembers a plausible answer. For a private collection, permission to retrieve the document and permission to expose its contents must survive the path into the response.

The result worth keeping is a question, its required source, the passages retrieved, the answer and the observed cost. That record lets you distinguish a cheaper working setup from one that merely returns fewer tokens.

Then trim what the generator never needed to read. Leave the passage that changes the answer.

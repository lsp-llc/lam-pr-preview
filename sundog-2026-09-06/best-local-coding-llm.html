Give Your Coding Model Room to Finish the Job

Choose a local coding model by its actual serving configuration, artifact and completed tasks. Reasoning effort, context and memory are separate controls.

By Sundog

6 September 2026

Suppose the model loads and its first patch looks sensible. Then the agent spends the rest of the session thinking, retries a tool call, and loses the thread of the file it was supposed to fix. A leaderboard position alone gives you little help diagnosing that session.

Start with the session you need to finish. On a fixed card, extra reasoning competes with your time budget and can consume part of the model's context window. The memory consequence depends on the architecture, the runtime's allocation, and what the harness retains between turns. There is no universal conversion from an effort label to gigabytes.[1]

Choose the serving configuration before you trust the rank

Keep enough context and output budget to finish your actual coding task, then spend the remaining time on reasoning. Compare models under that budget. A published score can nominate a candidate; it cannot certify the local setup you have assembled.

[OPINION] I would first change the serving configuration of a promising model before downloading another one. Fixing the wrong chat template or an undersized context window is a cheaper experiment than replacing the weights.

One model can occupy several leaderboard rows

A broad intelligence index and a repository-editing task measure different things. The index combines evaluations beyond coding, and its version belongs with any quoted score. It cannot tell you whether your agent will complete a particular change under your timeout with your tools.[2]

Qwen's own serving instructions make the practical problem less tidy. They expose reasoning effort, preserve thinking by default in the documented API setup, and warn that reducing effort can produce more retries and greater total latency or token use.[1] Shorter working on one attempt can become a longer job. Count the successful task, including its retries.

Your context setting determines the space you reserve

llama.cpp exposes separate controls for context size, parallel slots, fitting, and reasoning budget. Its fitting machinery adjusts unset parameters to available memory. Changing a reasoning budget does not necessarily release a preallocated cache; changing the reserved context or slot count may.[1] Inspect the startup allocation and effective context, then check the response's stop reason. A successful load is only the first check.

Qwen3.8 27B adds an architectural complication: its configuration repeats three linear-attention layers followed by one full-attention layer. llama.cpp implements hybrid memory with separate attention cache and recurrent state.[1] Multiplying all its layers by a conventional full-attention KV formula gives the wrong budget. So does assuming every thinking token remains in every later request. The harness decides what gets sent back.

Keep the local record small enough to use: exact model repository and revision, weight filename, runtime build, template, reserved context, parallelism, output limit, effort setting, and whether prior thinking is retained. Then repeat the same coding task. That is a comparison you can act on.

An 8 GB candidate still needs a context test

Ornith-1.5 9B, ornith-ai/Ornith-1.5-9B, is an ungated candidate with 9,653,104,368 parameters and 262144 declared positions. The owner's Q4_K_M artifact is 5,780,090,816 bytes.[3][4] That file size earns it an inspection on a small card. It does not prove a usable context length. Reserve space for the runtime and inspect the actual allocation before handing it a long editor session.

The Hub metadata says mit, while the linked LICENSE file returned 404 in the source check.[3] That mismatch deserves resolution with the publisher before a deployment that depends on the licence. A metadata tag cannot substitute for missing terms.

The owner reports SWE-bench Verified 70.6, SWE-bench Pro 47.5, and Terminal-Bench 2.1 46.2 under Terminus-2. Its terminal note specifies 128K context and five runs.[5] Preserve those conditions when reading the numbers. A model card with a large declared window has not promised that window on an 8 GB card.

The 16 GB claim belongs to a particular release

gpt-oss-20b, openai/gpt-oss-20b, has 21B total parameters, 3.6B active, an Apache-2.0 licence, and 131072 declared positions. OpenAI's card says it can run within 16GB of memory and says its evaluations used MXFP4. The ggml-org MXFP4 artifact is 12,109,566,624 bytes.[6][7] This is stronger fit evidence than a division of parameter count by two, while still leaving your runner, context and workload to check.

It also shows why benchmark provenance belongs beside the score. OpenAI reports 60.7 on SWE-bench Verified at high effort. NVIDIA's Nemotron comparison prints 52.44 for GPT-OSS 20B under its evaluator.[8][9] Different evaluation setups are enough to make those results unsuitable as a controlled comparison. The two reports do not isolate the harness as the sole cause of the difference.

Keep a coding benchmark, a broad intelligence index, and your own patch-completion test in separate columns.

A 24 GB shortlist needs an exact artifact

Qwen3.8 27B, Qwen/Qwen3.8-27B, is Apache-2.0 with 27,781,427,952 parameters and 262144 declared positions. The repository was created 5 August 2026. The ggml-org Q4_K_M artifact checked for this guide is 18,973,870,432 bytes.[10][11] Another publisher's Q4_K_M can have a different byte size. Record the repository and filename together.

Subtracting that disk size from the card label gives a rough screen, with inconsistent units unless you normalize them. It also omits runtime allocations. It cannot tell you whether xhigh will fit, whether medium will preserve forty thousand tokens, or whether either will fix your bug. Get those answers from the loaded configuration and a representative task.

The owner's table reports Terminal Bench 2.1 73.0 and SWE-bench Pro 61.7, beside 63.4 and 53.5 for Qwen3.6 27B. The two repositories share the printed parameter total and declared context.[10][12] Those results justify testing the newer candidate. They do not establish what the quantized local artifact will score.

Use the model configuration and the effective runtime limit when configuring a server. A leaderboard summary has another job.

Keep the capacity expansion separate from the model comparison

Qwen3-Coder-Next has 79,674,391,296 parameters under Apache-2.0. Its four Q4_K_M shards total 48,410,992,032 bytes, before cache and runtime. That calls for more memory, whether on several GPUs, unified memory, or a system that offloads part of the work.[13][14] Its report's SWE-bench Verified 70.6 under SWE-Agent and 71.3 under OpenHands remain results from those published setups.[15]

And verify that the named download exists before planning around it. The attempted Qwen/Qwen3-Coder-32B-Instruct and Qwen/Qwen3-Coder-32B identifiers returned HTTP 401, and the checked public Coder collection did not list a dense 32B release.[16] A 401 alone cannot distinguish a private, gated, or absent repository. Neither identifier supplies a verified candidate here.

Keep the run that finishes the task

I did not test these candidates on local hardware. The file sizes and reported scores identify things worth trying; they establish no local quality ranking.

[OPINION] I would choose a small set of real changes, fix the context and timeout, and compare the default effort with one lower setting before changing models. Keep the test cases unchanged. Count successful patches, tool failures, retries, elapsed time and truncation. A setting that thinks less but repeats the same mistake has saved nothing useful.

Keep the configuration with the result. Next week, when a new quant or runner arrives, you will have something better than a remembered leaderboard position to compare it with.
